# Moonshadow v1.3 规格（草案）：Phase 1 契约

> **状态：草案，未实现，不作为当前依据。** 本文件只写 **Phase 1 的接口契约**，不写实现。
> 已实现的系统以 **`docs/v1.2-spec.md`** 为唯一权威——凡本文件与它冲突，以 `v1.2-spec.md` 为准。
> 本文件不含任何打分参数取值（见 `v1.2-spec.md` §5.7、§9.2）。

## 0 本文件的定位

v1.2 封版时留下的核心缺口是：**压缩率 0.35x（膨胀），而「抽取器一改好一改坏」无法判定**。
Phase 0 把这个缺口量化了（口径见 `v1.2-spec.md` §9.3–§9.4，实现见 `eval.merge_headroom()`）：

| 事实 | 读数 | 出处 |
|---|---|---|
| 基线是「一条消息一张卡」，卡数 = 消息数 | `474` 卡 / `474` 消息 | `run_eval.py` |
| 结构口径的卡数下界（一张卡一个 `tier`，跨层级不能并） | `126` = Σ 每条用例出现过的层级数 | `eval.merge_headroom()` |
| 信息项口径的卡数参考值（`HARD_PATTERNS` 去重） | `139` | 同上 |
| 归并 + 去重（一字不删）的 token 上限 | **`1.000x`** | 同上，口径 B |
| 「只留含硬字段的句子」的理论并集下界 | `3.955x` | 同上，口径 A |
| 当前管线按 `≤10` 条消息切批，抽取器看不到整条会话 | 按 (批, tier) 归并只能到 `241` 卡 | `compress.compile_session(max_messages=10)` |

结论：**token 级抽象是硬前置**（归并只减卡数、不产生 token 收益），
Phase 2 的 LLM 抽取器不是可选优化；而卡数控制要进 Phase 1 的 I/O 契约。

## 1 Phase 1 的范围

**做**：定下抽取器的输入单元、跨批归并的责任归属、`T0/T1` 原文保留的方式，
并把这三条落到可执行的关卡与测试上（含 `verify.CARD_TEXT_FIELDS` 的同步调整）。

**不做**：不实现 LLM 抽取器（Phase 2）、不改 `scoring` 的任何默认值与参数（Phase 4）、
不动分组 `f`、不改动排序评测的任何口径。

## 2 已定的契约条款

**C1（定性内容必须可追溯）——已落地。**
`verify.verify_qualitative_retention(messages, cards)` 是硬关卡的一部分：
每条含**决策 / 硬约束 / 否定**（关键词表 `verify.QUALITATIVE_KEYWORDS`，与
`compress.TIER_KEYWORDS` 的 `T0/T2` 同源，由测试钉住同步）的消息，
必须至少有一张卡在 `source_ids` 里引用它；`T8/T9` 卡不算载体。
措辞可以不同（抽象是允许的），但追溯链不能断。

> **这条判据的边界必须写清**：它是**可追溯性**判据，不是语义判据。
> 它拦得住「消息连同 `source_id` 一起消失」（`tests/test_eval.py::DropQualitativeExtractor`），
> 拦不住「出了卡、引用了 source_id、但卡里没有那句话」（同文件 `StubCardExtractor`，
> 该形状按设计通过并由一条测试钉住）。语义层面归第二级模型模糊校验，硬关卡不假装能判语义。

**C2（压缩率的读法与适用域）——已落地。**
压缩率必须同时报**逐用例均值**与 **token 加权**两个口径，并按 `T0–T9` 报分层读数；
未产出卡的层级显示「—」而非 `0.00x`。适用域为**含跨消息冗余的长会话**。
口径细节见 `v1.2-spec.md` §9.2–§9.3。

**C3（卡数控制 + 归并责任划分）——已定。**
抽取器的卡数目标是 **`126`（结构口径）**，不是 `474`。结构口径的定义：
一张卡只有一个 `tier`，因此跨层级不能合并；下界 = Σ 每条用例出现过的层级数。
信息项口径（`139`）只作参考：它**不是卡数的数学下界**（一张卡可以装多个信息项），
它是「一个信息项一张卡」这个设计点。引用卡数目标时必须同时给出是哪个口径。

责任划分（Q1 + Q2 的裁决，写在这一条里）：

| 范围 | 责任方 | 要求 | 卡数效果 |
|---|---|---|---|
| **批内**（抽取器一次能看到的 `≤10` 条消息） | **抽取器** | 批内同一信息项只保留一处载体，其余不再各自出卡——`474 → 241` 这一档必须由抽取器一次产出，**不允许靠管线事后合并** | `474 → 241` |
| **跨批**（抽取器看不到的部分） | **管线** | 管线维护一个**信息项注册表**：遇到已在别批出现过的信息项时，只保留一处载体，其余卡改为 `source_ids` 引用 | `241 → 126` |

**C4（金标准集与关卡口径必须一致）。**
`eval/gold/*.json` 里每个 `expected_key_fields` 都必须能被 `verify.HARD_PATTERNS` 识别。
v1.3 Phase 0 修正了 14 个越界字面值（口径遗留，见 `v1.2-spec.md` §9.4），
修正方式是**换形式**（加反引号等），不是改值、不是扩大关卡口径。

**C5（`T0/T1` 不再靠卡内抄原文，逐字可用性走回链）——已定、已落地。**
`verify.CARD_TEXT_FIELDS` 不再包含 `raw_quote`；卡把原文整段抄一遍**既不计入卡文本、
也不进入压缩率**。`T0/T1` 的硬字段必须落在**卡内某个字段**里
（`facts`/`decisions`/`todos`/`constraints` 之一——C6 定下后不再要求必须是 `facts`），
逐字原文由 store 与 `source_ids` 回链保证（`sha256` 强制字节一致）。
`verify_no_silent_loss` 的路径相应地是两级：卡内文本 → 卡引用到的原文块。
详见 `v1.2-spec.md` §9.1（含这条判据的**边界**：它拦得住「消息没被引用」，
拦不住「引用了却没写」，后者由金标准的 `expected_key_fields` 那一侧拦住）。

**C6（卡内字段互斥）——已定、已落地。**
一张卡内，同一信息项只能有一个载体字段。

- 判定依据：信息项的**语义类别**，而非字面值。
- 决策句 → `decisions`，不再入 `facts`。
- 约束/否定句 → `constraints`，不再入 `facts`。
- 待办句 → `todos`，不再入 `facts`。
- 只有不落入上述三类的纯事实陈述，才进 `facts`。
- `summary` 是对该卡的整体概述，**不得逐字复述**任何已在
  `facts`/`decisions`/`todos`/`constraints` 中出现的句子。

违反 C6 的卡，由 `verify.verify_field_mutual_exclusion` 拒绝；该判据接入 `eval.run_case`
（违规记在 `CaseResult.field_violations`，并计入 `ok`）。判定用归一化后的整句，
只拒绝「同一句话写两遍」这种机械可判的重复；语义等价判断归第二级模型校验。

**为什么这条必须写进契约**：它是实测逼出来的，不是设计洁癖。同一句话既进 `facts`
又进 `decisions`/`todos`/`constraints` 时，token 加权压缩率是 `0.8421x`；
同样的代码、同样的卡数，**只把重复那一份去掉**就是 `1.4985x`（见 §6.1 的归因阶梯）。
这不是抽取器能力的天花板，是契约缺失造出来的天花板——
Phase 2 的 LLM 抽取器若不受这条约束，写出来照样撞上去。
`summary` 那一条同样必要：`summary` 一项占卡 token 的 `25.6%`（实测），
只堵字段不堵 `summary`，等于只堵一半。

**C6.1（基线豁免）——已定、已落地。**
`BaselineExtractor` 被指定为 v1.2 口径的参照点，其 C6 违规计入
`CaseResult.expected_violations`，**不作为 `run_eval` 的失败条件**。
此豁免**仅对 `BaselineExtractor` 生效**——实现上按抽取器的 `name` 判定
（`eval.BASELINE_IDENTIFIERS = ("baseline-rules",)`，另可用 `run_case(is_baseline=…)` 显式覆盖）；
任何其他抽取器（stub、Phase 2 的 LLM）的 C6 违规仍然让 `run_eval` 退出 `1`。

豁免的理由：基线的存在意义就是**展示「不遵守契约的形状是什么样的」**，
它必须保持原地不动。修它会使 v1.2 与 v1.3 失去可比性——
「规则版上限」这个数据点比一条绿色命令值钱。

把豁免写进代码而不是写进注释，是因为违规本身仍是**信息**：
`run_eval` 对基线退出 `0`，同时打印 `C6 违规 705 条（预期）`；
对 stub 退出 `0`、打印 `0` 条；对任何违反 C6 的非基线抽取器退出 `1`。

## 3 已定：Phase 1 的三条接口决定

> 三条都已拍板，Phase 2 的 LLM 抽取器接口就按此实现。

### Q1 输入单元 = **一批消息（`≤10` 条）**（已定）

不选单条、不选整个会话的理由：

- **单条**：一张卡对一条消息，正是 `474` 张卡的来源，等于把膨胀制度化；
- **整个会话**：超出抽取器的有效上下文，且冻结哈希无法在会话级校验；
- **一批**：与现有管线 `compile_session(max_messages=10)` 一致，不改架构。

### Q2 批内归并归抽取器，跨批归并归管线（已定）

- 抽取器在一批内可见全部消息，**批内信息项归并是抽取器的责任**；
  `474 → 241` 必须由抽取器一次产出，不能靠管线事后合并。
- 抽取器看不到跨批信息，**跨批归并是管线的责任**；
  管线用**信息项注册表**完成 `241 → 126`（相同信息项只保留一处载体，其余卡改为 `source_ids` 引用）。

责任划分同时写在 §2 C3，与「卡数目标 `126`」同一条。

### Q3 `raw_quote` 移出 `CARD_TEXT_FIELDS`，精度校验改走 `source_id` 回链（已定）

**移出，不保留。** 理由：`raw_quote` 留在卡里，压缩率就没有意义——
变更前 `T0` 只有 `0.292x`，永远救不回来，LLM 抽取器接进来也只是把逐字抄从 `raw_quote` 搬到别处。

六条连带改动**必须同批完成**，一条不落：

1. `verify.CARD_TEXT_FIELDS` 移除 `raw_quote`；✅
2. `card_text_many` 同步（它由 `CARD_TEXT_FIELDS` 驱动，不再把 `raw_quote` 拼进卡文本）；✅
3. `verify_no_silent_loss` 改为两级：卡内文本 → 卡引用到的原文块（新增 `sources` 参数）；✅
4. 抽取器 I/O 契约写明：**`T0/T1` 的硬字段进 `summary` 或 `facts`**，不是靠复制原文段；✅（本节与 §2 C5）
5. 测试：卡文本不含 `raw_quote`；硬字段在「卡内」或「回链」至少一侧可查；回链追不回没被引用的消息；✅
6. 重跑 `run_eval`：`T0` 压缩率跳升是**预期**，跳升幅度记进差异表。✅（见 §5）

**已知代价与边界**：`verify_no_silent_loss` 的调用代价上升（回链取原文）。
金标准集 25 条、每条几百到上千 token，开销可控；规模上万时需要缓存——留给 v1.4。
另一条代价更重，必须写明：**回链打开后，`key_field_recall` 在原文可达时恒为 `1.0000`**，
全局硬字段扫描从「内容判据」退化为「可达性判据」（实测见 §5 与
`tests/test_eval.py::test_global_sweep_is_now_backlink_based`）。
因此关卡的实际分辨力落在两处：金标准的 `expected_key_fields`（卡内文本判据）与 C1 的定性内容判据。
要让硬字段扫描重新有分辨力，只能改 `v1.2-spec.md` §10 的原文保留策略——那是它天然的作用点。

**风险提示（原样保留）**：回链成本随用例规模线性增长；上万条用例需要缓存，属 v1.4。

**C8（`summary` 必须承载内容）——已定、已落地。**
每张卡的 `summary` 必须满足：

- **C8.2（重定，方案 B）：只要求覆盖硬要点。** 对 `decisions`/`todos`/`constraints` 中的每一条，若它含 `HARD_PATTERNS` 的任一匹配，则 `summary` 必须逐个覆盖这些匹配（不要求连续、不要求逐字）；**不含 `HARD_PATTERNS` 的条目不要求被 summary 提及**——LLM 抽象掉非硬要点是正常行为。
- 旧判据（4 字连续片段共享）已废弃：它是逐字级代理，会把合规的抽象判成违规。
- **C8.3（长度）**：`summary` 长度应 ≥ 该卡字段 token 之和的 `10%`，且 ≤ `40%`。
  **当满足 C8.1 与 C8.2（覆盖全部要点）所需的最小长度超过 `40%` 上限时，以覆盖为准，
  上限自动放宽至覆盖所需的最小长度。此放宽不构成违约。**
  C8.3 的实现方式是不引入语义判断：**先把「提及」算出来，再判长度**——
  `长度 > 40%` **且**存在未覆盖的要点，才算违规；超上限本身不违约，
  于是「覆盖所需的最小长度」这个不可机械判定的量根本不需要被计算。
  （实测：本套金标准集的 `474` 张基线卡里，`提及所需最小长度 > 40% 上限` 的卡是 **0** 张，
  所以这条优先级目前是**预防性条款**，不是为某张卡开的特例。）

违反 C8 的卡由 `verify.verify_summary_substance` 拒绝，判据接入 `eval.run_case`
（记在 `CaseResult.summary_violations`，并计入 `ok`）。**规则基线豁免适用（沿用 C6.1 语义）。**

机械化的方式：「覆盖要点、不要求逐字」实现为**共享至少一个 `4` 字连续片段**
（`verify.SUMMARY_MENTION_CHARS`）。它拦得住 `summary="T0"` 与「见字段」，
但拦不住「把片段拼起来当概述」——那是语义摘要的门槛，也是漏洞 #10 的同一条缝。

**定位（重定后）**：C8 与 C1 **职能互补但不重叠**——C1 判「硬要点有没有载体」，C8 判「summary 是否覆盖硬要点」。C8 不拦非硬要点的抽象，那是 LLM 抽取器的正常行为。`summary="T0"` 这类空壳仍被拦（硬要点未覆盖）；「见字段」式拼接只要覆盖硬要点即通过。约束力确实下降了，但那是**从错误方向收回**（原判据拦合规的抽象，是缺陷不是力度），不是削弱。

**为什么必须有这条**：`summary` 占卡 token 的 `25.6%`（实测），而 C6 只禁止它复述、
不要求它有信息量；没有 C8，一个 `summary="T0"` 的抽取器能拿到好看的压缩率却什么也没说。
代价也是实测的：C8 合规的片段摘要比 `summary="T0"` **多花 `0.19x` 压缩率**
（`1.4985x → 1.3063x`）——这是为了让读数可信而付的钱。

**C7（一句话同属两类时的优先级）缓办**：它本质是语义判断，LLM 读完整句自然能分；

## 5 Q3 的口径差异表（重跑 `run_eval` 的实测）

### 6.3 形状守卫拦下的读数（审计链）

`assert_comparable` 接入阶梯后，立刻**拒绝**了两对比较，其中一对就是本文 §6.1 里那条 「C6 值 0.66x」：

| 对比 | 声明的自变量 | 结果 |
|---|---|---|
| 现状 vs A（复述） | `facts` | **拒绝**：`field_tokens[summary]` 3264 vs 5178 未声明 |
| 现状 vs C（只 facts） | `decisions`/`todos`/`constraints` | **拒绝**：`facts`、`summary` 也变了，未声明 |
| 现状 vs D（极简摘要） | `summary` | **可以比较**：其余字段逐一相同 |

两条被拒的原因是同一个：**摘要（片段摘要）是从字段派生出来的**，任何字段级消融都会顺带改摘要长度。所以「A→B 值 0.66x」不成立——不是测量误差，而是**测量对象不是它声称的那个东西**。

**阶梯重新设计后的结论**：本 stub 只能给出**一个**干净的单变量归因——D（摘要写法），成本 = `1.4985x - 1.2734x` = **`-0.225x`**。字段级消融（C6/facts）要成为干净对照，必须让摘要**不再从字段派生**（例如固定从原文取素材），否则它永远是「改了字段 + 顺带改了摘要」的复合变量。

**空壳仍被拦，但要看清它是怎么合规的**：stub 的 C8 违规为 `0`，是因为它被**改成显式覆盖硬要点**，不是因为它天然遵守 C8。对比同批三条 LLM dump 的 `todos`/`constraints` 硬要点覆盖：7 个硬要点里 **漏了 3 个**（`17` 的 `18 万`、`20` 的 `2026-10-15` 两次）——**`decisions` 里 0 个硬要点**，所以 C8.2 的真实压力点在 `todos`，不在 `decisions`。


**待办（v1.3 收尾清理，本轮不做）**：把 stub 的 `summary` 改为**从原文取素材**，而不是从字段派生。这样 `facts`/`decisions`/`todos`/`constraints` 的消融就不再连带改摘要长度，A/B/C 全部回到「单变量」状态，C6 与逐句字段能各自给出干净读数。本轮不做，因为**归因已经闭合**：摘要写法值 `0.225x`、抽象值 `1.2x`，两项相加约 `1.4x`，正是参照线 `1.2734x` 到 `>= 2.0x` 的差值——继续在 stub 上挖不再有新的决策价值。

**四处 `0.66x` 均已带作废标记**，且每处的作废理由都是同一条守卫结论：「现状 vs A」被 `assert_comparable` 拒于生成数字之前，理由是 `field_tokens[summary]` 未声明地变了（`3264 vs 5178`）——即该对比是**复合变量**，不是它声称的「C6 的价值」。

### 6.4 开放问题（v1.4 议题）：记忆的冲突与演化

> 标题即议题名。**本节不做任何实现**，只把三条缺口写下来——因为不写下来，
> Phase 2 的抽取器会**绕开**它们，把矛盾静默地复制到每一张卡里。
> 编号用 `OQ` 而不是 `Q`：§3 的 `Q1–Q3` 是 Phase 1 已决的接口决定，同文档里不能有两个 Q1。

| 场景 | 现有防御 | 缺口 |
|---|---|---|
| 过时（同 subject） | `claim.valid_from`：同一 `(subject, predicate)` 上更晚者胜 | 缺「新卡是否推翻旧卡」的**自动检测** |
| 过时（异 subject） | 时间衰减只压低分数（`m = f + (1-f)δ`） | **无硬性裁决**；两张卡可以长期共存 |
| 错误总结 | C1 + `source_id` 回链 | **被动**：下游不读原文就失效，错误沿召回链传播 |
| 矛盾偏好（同粒度） | `valid_from` 裁决 | 前提是能判定两侧 subject 相同 |
| 矛盾偏好（异粒度） | **无** | 没有粒度识别，会把局部偏好误判成全局推翻 |

**OQ1：如何检测「新卡推翻旧卡」，而不依赖人工标 `superseded_by`？**
现状：`superseded_by` 只在被**显式标记**时生效。系统没有检测「新卡是旧卡的对立面」的机制，
于是两张矛盾卡共存。时间衰减帮不上忙——它只能压低分数，不能判断「过时」：
一张 T2 卡半年没更新，`m` 会掉，但只要 `q` 仍高于 `θ`，它照样被召回。

**OQ2：如何判定两张卡是「同粒度冲突」还是「异粒度并列」？**
这是最难的一条。例：卡 A（T1/opinion）「以后都用 4 空格缩进」（三年前），
卡 B（T2/opinion）「这个项目用 2 空格缩进」（上周）。两张卡都合法、都过 C6/C8、都会被召回。
当前机制处理不了，有两个方向的错：`valid_from` 裁决要求同一 `(subject, predicate)`，
而「以后都用」与「这个项目用」**未必同 subject**；即使 subject 相同，时间裁决会选 B——
但 B 是**局部**偏好，不是对 A 的**全局**推翻，系统把「上下文不同」误判成「更新推翻」。
反过来，若 subject 不同，两张卡共存，LLM 生成回答时可能同时引用两个矛盾偏好，输出自相矛盾。

**OQ3：如何在召回时给下游标明「此处存在冲突，需裁决」，而不是把矛盾静默传给 LLM？**
现在没有任何一条通路把「冲突」这件事本身当作信息传给下游。

**一条关于解法的预判**：这三问的答案很可能需要 **claim 级别的语义索引**——
不只是 `(subject, predicate)` 的字面匹配，而是嵌入向量相似度 + 粒度识别。
那会引入本仓库目前刻意没有的东西（向量模型、阈值、以及「相似到什么程度算同一 subject」这类新参数），
因此它是 v1.4 的议题，不是 v1.3 的补丁。

**v1.3 的边界**：v1.3 要证明的是「契约可执行」（C1–C8.2 + 守卫 + 基线豁免），
不是「语义冲突可解」。把这三条写在这里，是为了让 Phase 2 的抽取器**知道自己在绕开什么**。
