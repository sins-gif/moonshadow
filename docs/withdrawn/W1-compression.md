## 1 撤回的到底是什么

**撤回的是「压缩」这个动词，不是分层记忆这件事。**

现在做的是**摘要**：把一条消息摘成一张短卡。但摘出来的东西比原文长——所以叫「压缩」不成立。
按读数说：原文 `241,160` token 的输入，产出 `436,156` token 的卡（同一批数据的临时库实验），
即卡是原文的 `1.8` 倍。

**没有撤回的**：T0–T9 分层、时间门、有界乘性修正、召回编排、装箱、契约与守卫——这些照旧成立（§3）。

## 2 为什么撤回，而不是继续调参

三个互相独立的原因，每一个都能单独否掉「再调调就好」：

1. **不是阈值问题，是抽取器只会「抄」不会「并」。**
   规则的基线抽取器是**一条消息一张卡**：`facts` 复述关键字段，`decisions`/`todos`/`constraints`
   再把整句抄一遍。同一批字段按消息数重复 N 次，卡自然比原文大。
   这一条由 `run_eval.py` 的 `C6` 违规计数佐证：基线豁免 `705` 条违规（预期）。
2. **全局 `2.0x` 在算术上就不可达。**
   卡 token 占比：保持组 `T0–T2` 是 `64.8%`、压缩组 `T3–T7` 是 `34.9%`、豁免组 `T8/T9` 是 `0.4%`。
   即使压缩组做到无穷大，全局上限也只在 `≈1.41x`。所以「把压缩率调上去」这件事，
   在现有分组下**没有可行解**，除非先改「哪些层该压」。
3. **验收口径已经改过一次，说明旧口径本身就不成立。**
   全局 `2.0x` 被拆成「分层目标 + 信息条目」两条判据——这不是文字游戏，
   是承认「一个全局数字量不出一件事」。

## 3 不受影响的结论（各带复算命令）

| 结论 | 复算命令 | 期望 |
|---|---|---|
| 定值下两集合排序全对 | `python tools/run_holdout.py` | 开发集 `1.000`、留出集 `1.000` |
| 全部负例被生产门真的挡住 | `python tools/run_gate_audit.py` | 违规 `0` 张 |
| 用例不违反层级窗口 | `python tools/run_case_audit.py` | 违规 `0` 张 |
| 留出集未被改动 | `python tools/run_split_integrity.py` | 9 条 SHA-256 与冻结值一致 |
| 有界修正的反转上界成立 | `python tools/run_drift_check.py` | 越过 `1/f` 的 `0` 组 |
| 关键字段不丢 | `python tools/run_eval.py` | 保留率 `1.0000` |
| 全量测试 | `python -m unittest discover -s tests` | 退出码 `0` + `OK` |

**一句话**：`0.498x` 否掉的是「压缩」这个词，不是这些读数。

## 4 为什么不写「放弃 v1.2」

`v1.2.0` 的**版本级目标**是（`v1.2-spec.md` §0 的表）：

> 把 v1.1 已确定的形式与结论落成**唯一的一组定值**，并把「用例集可否被随手修改」变成可强制的契约

这一条**达成了**：定值落地、切分冻结、15 条发布验证命令、守卫齐全。
没达成的是**协议级**的「压缩」。两层判据不同，混在一起写会把达成的那半也一起拖走——
对本仓库的读者与外部汇报都是净损失。

所以归档动作的精度是：**撤回一条宣称**，冻结一个版本，其余照旧。
