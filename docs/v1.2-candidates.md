## 0 总评

**产品愿景（个体化记忆曲线）成立；论证链条不成立。**

提案第 6 节写「参数变成了数据驱动的自适应变量，因此彻底解决了占位值问题」。
这句话把两件不同的事绑在了一起：

| 问题 | 正确的解法 | 提案的解法 |
|---|---|---|
| 参数没被数据验证 | **测量**（扫描 + 留出验证） | 让它自适应 |
| 参数应当因人而异 | 产品目标，需单独设计 | — |

自适应**不会**减少未知量，它让未知量从 11 个变成约 30 个：

| | v1.1 | v1.2 提案 |
|---|---|---|
| 半衰期 | 10 个 `h` | 10 个 `base_h` + 10 个 `min_h` |
| 时间下限 | 1 个 `f` | 4 个网络区间（≈8 个端点）+ 1 个 `agent_factor` |
| 强化系数 | — | 1 个 `α` |
| **合计** | **11** | **≈30** |

而且自适应引入**反馈闭环**，使效果**无法在静态用例集上测量**——同一张卡在不同时刻分数不同。
所以我们现有的整套排序评测（`sweep_floor`、`case_floor_bands`、可行区间）**输入契约就变了**。

**一句话**：自适应让验证更必要，不是更少。

## 2 需要修正的技术缺陷

### 2.1 `min_h` 是死配置

公式 `h_new = h_base·(1 + α·log(1+access_count))` 在 `access_count = 0` 时等于 `h_base`，
**只增不减**。配置里 T1 的 `min_h: 180` 在任何公式中都没有出现。
要么补一个「长期未访问则向 `min_h` 收缩」的项，要么删掉该字段。**当前是规范空洞。**

### 2.2 与已有的 tier 晋升机制复合

v1.1 的 `next_tier` 已经在做「近 30 天 ≥ 5 次访问且跨 ≥ 3 个会话 → 升 1 级，上限 T2」。
再加一层 h 延长，**两个机制都在奖励访问**：

```
一张 T5 卡：先因访问升到 T2（h: 14 → 180），再乘 (1+0.35·log(1+n))
n = 1000 时系数 3.4  ⇒  h_eff = 612 天
```

这个复合效果显然不是设计意图。**必须二选一，或明确定义复合规则。**

### 2.3 `f` 乘积可能越界

`f = base_f(network) × agent_factor` 是**乘积**，不是有界映射。
`base_f = 0.90`、`agent_factor = 1.2` ⇒ `f = 1.08 > 1`。
此时 `m = f + (1−f)δ > 1`，**时间开始给分数加分**，直接违反定理 2 与命题 1 的值域。
必须夹到 `[0, 1]`。

### 2.4 无 `max_h`，半衰期无界增长

α = 0.35、访问 1000 次 ⇒ 系数 3.4×。缺少上限，一张卡最终免疫时间。

### 2.5 反馈锁定

`access_count` 由「被选入上下文」增加（这点提案写对了），而是否被选入取决于 h。
于是：**被召回的更容易被召回**。v1.1 的 `next_tier` 至少有「上限 T2」这条安全轨，
而 h 公式**一条都没有**。需要上限，或改用跨会话计数等独立证据。

### 2.6 配置与命名空间

- `agent_decay_config.json` 缺 JSON Schema、缺版本号、缺缺省回退。仓库现有纪律
  （`schema.json` + 强制校验）应延伸到配置文件。
- **跨 agent 记忆共享语义未定义**：多个 agent 是共享同一批记忆卡、只是衰减法则不同，
  还是各有独立存储？这是「个性化记忆」里最有意思的问题，提案是空的。
- Roadmap 提到的 `src/moonshadow/config.py` 与 `src/moonshadow/recall.py` **都不存在**：
  配置现在是 `scoring.py` / `tiers.py` 的模块常量，召回逻辑分布在
  `scoring.py` / `pack.py` / `rank_eval.py`。

### 2.7 测试影响被低估

「151 个断言中有部分需要重置」不足以描述（现行条数以
`python -m unittest discover -s tests` 的输出为准）。真实影响是：

- **排序评测的输入契约变了**：分数依赖访问历史，用例文件需要附带轨迹；
- `test_constants.py` 那批「常量守卫」的存在意义整体改变：从「常量值不能漂」
  变成「配置文件合法且派生值与文档一致」。

## 3 与现有证据冲突的三条

### 3.1 网络 `f` 区间与用例 05/06 冲突（可立即检验）

现有扫描结果（`run_rank_eval.py`，步长 `0.005`）：用例 `05-status-stale-strong` 与
`06-status-without-markers` 要求**被顶掉的那张卡** `f ≤ 0.690`（两条的可行区间均为 `[0.000, 0.690]`）。
而提案给：

| 网络 | 提案 `f` 范围 | 与 `[0.000, 0.690]` 的关系 |
|---|---|---|
| `experience` | `0.65 – 0.80` | **部分重叠**：`[0.65, 0.690]` 内成立，超过 `0.690` 会翻转期望 |
| `opinion` | `0.75 – 0.90` | **无重叠**：整段在 `0.690` 之上 |

**修正记录**：本节此前写「要求 `f ≤ 0.634`，两者都在这条线之上」。`0.634` 是**旧用例集**的数字——
`05`/`06` 的陈旧的卡当时是 `T4/Δ=45`，超出 T4 的 30 天窗口，且区间计算受一张超窗正例影响。
把卡龄修到窗口内之后，这两条的可行区间上界是 `0.690`。
因此冲突范围由「`experience` 与 `opinion` 两段都不重叠」缩小为「只有 `opinion` 一段不重叠」。
严格数值仍需要按 per-card `f` 重扫，但方向与量级明确。

这条要么改提案的 `f` 表，要么**重新论证 05/06 的期望**——后者等于承认
「陈旧的 experience 卡不该被新信息顶掉」，那是一种不同的产品主张，不是参数调整。

### 3.2 「T7 噪音抑制率 +30%」——该项收益 v1.1 已经拿了

按定义 6，T6/T7 需要 `Δ ≤ 7 天` **且** `q > θ′`。超过 7 天的 T7 卡**根本进不来**，
与 `f` 无关。因此「500 轮后 T7 自动沉淀」在 v1.1 里是 100% 成立的，**该指标已经饱和**。

**并且这暴露一个必须钉死的规范空洞：模拟器没有定义「一轮 = 多少模拟时间」。**

| 时间模型 | 谁在抑制 T7 |
|---|---|
| 一轮推进时间 | 门的 7 天窗口完成抑制，`f` 的贡献被掩盖 |
| 500 轮都在同一天内 | T7 卡仍在窗口内，抑制完全靠 `f` |

**同一份模拟，两种时间模型会得出相反结论。**

### 3.3 `network` 是未测量的推断标签——但「不可用」这个结论被后续实验推翻

v1.1 否掉「按查询意图切换 `f`」的理由是：被门控的类别若靠**推断**，其错误率就变成 `f` 的错误率
（意图识别实测 recall 0.500）。`network` 初看是同一类问题——它由抽取器赋值，不是已知元数据。

首次测量（`eval/network/cases.json` 的 24 条，基线规则）得到 **0.375**，
且 `world` 与 `observation` **两类从未被预测出来**。据此本文件此前写下了
「network 是未测量的推断标签，因此网络门控路线不可行」。**这个结论是错的**，理由如下。

#### 后续诊断实验（`tools/run_network_eval.py`）

把标注集扩到 48 条（24 开发 + 24 留出，留出在规则改进前写完），
并写一个不依赖 `tier`、四类各有类级词汇的规则（`network_rules.py`）后：

**复核说明（v1.2 定值落地后重跑）**：下表与当前工具输出**逐格一致**，无需修改。
该实验只依赖 `eval/network/cases.json`（未参与本次重划切分），因此不受排序用例集变动影响。

| 规则 | dev 严格 | dev 可达 | holdout 严格 | holdout 可达 |
|---|---|---|---|---|
| v1 基线（3 分支，依赖 tier） | 0.375 | 0.478 | 0.250 | 0.217 |
| **v2（4 类词汇，不依赖 tier）** | 0.958 | 0.957 | **0.958** | **1.000** |

- **严格** = 必须等于唯一标注；**可达** = 只在「有正确答案」的用例上统计（分类器质量）。
- **schema 上限** = 有正确答案的用例占比 = `0.958`（每集合各有 1 条**无正确类别**）。

**三条修正：**

1. **`0.375` 是「6 个关键字的正则」的分数，不是 schema 的难度。**
   换成一个真正的四类分类器后，**有答案的用例全部答对**（holdout 可达 `1.000`）。
   因此**「network 赋值不可靠」不成立**——不可靠的是基线实现，不是这个维度。
2. **去掉 `tier` 依赖修掉了泄漏。** v1 里「重构时**不要**删除 …」因否定词被判成 T0、
   进而 `network` 变成 `world`；v2 不再使用 `tier`，该条正确判为 `experience`。
3. **剩下的唯一损失是 schema 缺口**：每集合 1 条属于「待办/承诺」，
   而四类网络装不下它（见本文件 §6 的开放项与 `v1.2-summary.md` §6 第 5 项）。
   这部分**任何分类器都补不上**——加规则或换模型都不改变「这一条没有正确类别」。

#### 因此对提案的影响方向反转

| 先前的判断 | 修正后的判断 |
|---|---|
| network 门控依赖不可靠标签，不可行 | **赋值不是瓶颈**（可达 `1.000`）；真正的障碍是①排序用例不带 network 标注，②分类法缺一类 |
| 建议改为人工配置或微调 | **两者都不为准确率所需**。人工配置仍可用于「控制权」诉求，但不是可靠性诉求 |

**这个结论对 `v1.2-roadmap.md` 的影响**：网络分组**不在 v1.2 范围内**，
但排除它的理由从「不可行」改为「需要补排序用例的 network 标注 + 先补分类法缺口」。

#### 本次诊断的效力边界

留出集与规则由**同一作者在同一轮**完成（先写用例、后写规则），
因此它检验的是「没有针对开发集数值迭代」，**不等于**「规则作者没见过留出文本」。
要严格化需要：冻结规则后由**第三方或另一数据源**另出用例。
此外，`v2` 在开发集上有 1 条真实错误（「刚看到…」未被识别为观察类），
**没有在测量后修改规则**——修它会消耗掉留出集的一次性，须另建新留出集方能确认。

### 3.4 「对冲 y8y / hecate」不可用

两者的实际行为未知。而且 v1.0 明确把 `network` 字段记为**借自 y8y 的亮点**——
如果 y8y 已在用 `network`，那 network 门控就不是差异化。**核实前不能写进相关工作。**

## 4 模拟器的四个未定义项（这是提案最好的部分，但还不完整）

明确肯定：**自适应参数必须用轨迹评估，静态用例集测不出来。** 这是提案里最有价值的一句话。

但需要补：

| 缺口 | 后果 |
|---|---|
| **任务级真值**：「成功召回 T1 卡的**概率**」——谁判断「应该被召回」？ | 需要模拟用户提出 N 个正确答案依赖该卡的问题。没有这个，指标不可计算 |
| **回答质量**：Token 节省率的前提 | 这是最难的部分，被一句「保持同等回答质量的前提下」带过 |
| **时间模型**：一轮 = 多少模拟时间 | 决定 T7 抑制由门还是由 `f` 完成（§3.2） |
| **效度声明**：模拟用户由提案作者编写 | 测的是作者的假设，不是系统——与手写用例同一个陷阱，升了一层 |

## 5 提案中应完整保留的部分

1. **交互模拟器**（含上述四个补丁）——自适应参数的唯一正确验证手段。
2. **`base_half_life_days` / `current_half_life_days` 分离**——可审计、可回滚。
3. **分类 `f` 的理论收益**（这是提案最硬的一块，见下）。
4. **`access_count` 语义**——与已有设计一致。

### 5.1 分类 `f` 为什么优于被否掉的意图切换

| | 意图切换（v1.1 已否） | 分类 `f`（v1.2 提案） |
|---|---|---|
| 类别来源 | 查询文本推断 | 卡的属性 |
| 实测可靠性 | 状态类 recall：开发集 `0.444`、留出集 `0.250`（`run_rank_eval.py` / `run_holdout.py`） | **已测**：v2 规则 holdout 可达 `1.000`、dev 可达 `0.957`（§3.3） |
| 结论 | 无增量、负收益 | 理论收益真实，可靠性的障碍已从「分类器不准」改为「标注缺失 + 分类法缺口」 |

关键差别：意图必须从文本推断，而类别是卡的属性。**但「是卡的属性」不等于「赋值可靠」**——
§3.3 就是这句话的实测。

### 5.2 理论收益：从单一上确界到一族上确界

若 `f` 随类别变化，则由定理 3：

```
反转 ⟺ r_A/r_B < m_B/m_A，其中 m_i ∈ [f_{c(i)}, 1]
⇒ 不反转的充分条件：r_A/r_B ≥ 1/f_{c(A)}
```

**上界取决于「被顶掉的那张卡」的类别。** 按提案的区间：

| 类别 | `f` | 可反转上界 `1/f` |
|---|---|---|
| `opinion` | 0.85 | 1.18 |
| `experience` | 0.70 | 1.43 |
| `world` | 0.60 | 1.67 |
| `observation` | 0.25 | 4.00 |

语义正好符合直觉：**观点几乎无法被新信息顶掉，观察极易被顶掉。**
这不是参数微调，是把 v1.1 的单一上确界升级成**一族上确界**——也是本提案最值得保留的贡献。

**但要注意**：`observation` 的 0.20–0.45 对应上界 2.2–5.0，是**很弱的保护**。
它让 observation 卡几乎纯按新鲜度排序——在状态类查询里正确，在日常事实类查询里
会把相关的旧卡埋掉。两个方向都有用例，需要实测（§7）。

**并且 v1.2 之前应先清掉 v1.1 的四个已知缺陷**——v1.2 已清掉其中三个，逐条记账：

| v1.1 的已知缺陷 | 现状（证据） |

### 7.1 四条结论（数字已按加入边界用例后的用例集与两阶段扫描重导）

**1. 分组 `f` 可行，交集非空。** 粗网格上交集有 `24` 点；采纳的单一解
`(0.5925, 0.5925, 0.5925)` **在交集内**——即单一常数解是分组解的一个特例，分组没有破坏已有结论。

**2. 最窄约束**从 `high` 组变成了 **`low` 组（T6–T9）**：开发集粗网格上 `low` 宽 `0.119`
（`high` `0.197`、`mid` `0.632`）；留出集上仍是 `high`。**「哪一组在压住可行区」是用例集的函数**，
不是分组的固有性质——每批用例都要重测。
**旧结论「真正的约束是 `mid`（T3–T5），宽 `0.08`」已失效**：它建立在旧的超窗用例集上，
而超窗候选与超窗正例正是 §3.1 与 §8.1 记录的那批（现已全部修正）。

**3. `low` 组的自由度仍缺证据支撑。** 开发集正例分布为 `T0 2 / T1 1 / T2 7 / T3 2 / T4 2 / T5 27 / T6 1 / T7 1`，
`T8` 与 `T9` 为 `0`；留出集 `T8` 有 1 条、`T9` 仍为 `0`。
（注：加入边界用例后 `low` 组在开发集上的可行区间反而成了最窄的一组，见结论 2——
这**不是**「有数据支撑了」，而是三条新用例把 `low` 的一段挤掉了，其根因仍是 T8/T9 缺正例。）

**4. 分组收益的量级仍受粗网格限制，本版不据此定值。** 交集只有 `24` 个粗网格点、
逐轴精度 `0.0395`，因此**不给出**分组 `f` 的推荐取值。采纳的仍是单一常数 `f = 0.5925`
（`v1.2-spec.md` §0.3 明确本版不做分组下限）。**旧结论「余量从 `0.020` 提到 `0.060`、
约 4 倍」已失效**：那是单阶段 `0.02` 网格上的读数，且当时单一 `f` 的窗口只有 `0.026` 宽。

### 7.2 一个必须一并说明的技术细节：可行区不是盒子

逐轴区间的组合**不可自由使用**：

```
交集外接盒：high 取 4 个粗网格值 × mid 4 个 × low 4 个 = 64 点
其中真正可行：24 点 = 37.5%
```

也就是说，`high ∈ [0.55, 0.67]`、`mid ∈ [0.51, 0.63]`、`low ∈ [0.51, 0.63]` 这三句话
**不能当成三个独立约束**去任意组合——只有约三分之一的组合成立。

**旧数字已两次作废**：「逐轴取值数 8 × 5 × 36 = 1440，其中可行 776 = 53.89%」（旧用例集 + 单阶段 `0.02` 网格），
以及「48 点中 12 点 = 25.0%」（加入边界用例前的 `0.055` 网格）。
结论方向不变（仍是**非盒形**），比例随用例集与步长变化。

### 7.3 与提案 `f` 表的对照：冲突由「两段都不重叠」缩小为「`opinion` 一段不重叠」

提案给 `experience` = `0.65–0.80`、`opinion` = `0.75–0.90`。映射到 `mid` 组
（T3–T5 是决策与日常事实所在的层）：

```
mid 的可行区间上界（粗网格）= 0.632
experience 区间 = [0.65, 0.80]  ⇒ 无重叠
opinion    区间 = [0.75, 0.90]  ⇒ 无重叠
```

**注意本轮方向又变了**：加入边界用例后 `mid` 的粗网格上界由 `0.66` 降到 `0.63`，
于是提案的两段**又都落在可行区之上**。这恰好说明「提案 `f` 表是否冲突」**完全取决于当前用例集**：
上一轮说「`experience` 有一段重叠」，本轮说不重叠，两轮都不是稳定结论。

由于粗网格逐轴精度只有 `0.0395`，`0.63` **不能**当作精确上界使用——
诚实表述是「`mid` 的上界落在 `(0.632, 0.672)` 内」。要给出结论必须先做更细的全空间扫描
（当前成本不允许，见 §7.4）。

### 7.4 三个方法学提醒

- **扫描步长必须能整除被讨论的取值，且这一点已被强制。** 早期版本用步长 `0.05`，
  而当时的采纳值 `0.62` 不是它的倍数，导致网格漏掉采纳值、得出「单一解不在交集内」的假结论。
  现由 `rank_eval.require_step_divides` 在构造扫描时**直接抛错**（不再是警告）。
- **整除还不够：网格必须对齐。** 本轮又踩到第二层坑——`ranges` 细扫原先从区间下界起算
  （`low + i·step`），当 `low` 不是步长整数倍时整张网格偏移，采纳值仍会漏掉。
  现已改为**对齐到全局步长网格**（`ceil(low/step)·step` 起算），实测采纳值回到细扫可行集内。
- **交集在粗网格上计算，是保守的内近似。** 逐轴精度只有 `0.0395`，细扫只提高盒内分辨率、
  **不改变交集范围**。所以只能给出「上界落在 `(0.632, 0.672)` 内」这类粗陈述，不能据此定值。
- **「最稳点」会被扫描边界污染。** 边界附近的点周遭没有不可行点，余量会被高估。
  报告最稳点时必须标注它是否落在扫描域边界上（`v1.2-roadmap.md` §7.7）；
  本节因此**不报**分组 `f` 的最稳点。
