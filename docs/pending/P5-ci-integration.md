# P5 · 把压力测试门接进 CI

| 项 | 内容 |
|---|---|
| **目标版本** | v1.2.x |
| **想法** | `tools/stress_recall.py` 自称「可进 CI」，但仓库里**没有任何 CI 配置**在跑它。要真的守住性能，得让它在一个固定的机器上定期跑，红了下不来 |
| **可实现性** | **解锁条件**（三条）：① `P1`–`P4` 至少 `P1`、`P2` 已解锁（否则一进 CI 就常红，等于没有信号）；② 定跑哪几档（建议 `--cards 1000,10000`，约 40 秒；`20000` 档要 1 分钟以上，不进默认）；③ 定在哪种机器上跑（性能门**不能**跑在共享 runner 上——那台机器的抖动没有基线，详见 `P4` 的「机器标识」） |
| **判定方法** | CI 跑一次，退出码为 `0`；再人为把门限调紧一次，退出码为 `1`（证明它真的会拦） |
| **当前状态** | **未解锁**——`P1`/`P2` 未解锁，且没有 CI 配置 |

## 为什么现在不能做

性能门和正确性门不一样：**它的读数依赖机器**。把「本地 300 ms/千卡」的门设在 GitHub 共享 runner 上，
要么天天红（runner 慢），要么为了不红把门放宽到没有意义。**先解决「在哪跑、和谁比」**（P4），
再接 CI。

## 解锁后的验收

- 有 CI 配置（`.github/workflows/*.yml` 或等价），至少有一个 job 跑 `tools/stress_recall.py`；
- 该 job 的机器类型写在 README 的「复跑」一节；
- 从 CI 上取的读数**不混进**本地基线（`机器标识` 不同则拒绝比较）。
