# P4 · 性能测量落盘做基线，判「比上次慢了多少」

| 项 | 内容 |
|---|---|
| **目标版本** | v1.2.x |
| **想法** | 现在 `tools/stress_recall.py` 只判**绝对门限**（`A + B·n`），判不了「同一档比上次慢了 8%」。要抓回归，得把每次测量的区间落盘成基线，下次运行时对比。对照规则已经定好：**只有 B 的 `max` < A 的 `min` 时才能说「B 比 A 快」**（区间重叠不许宣称变快） |
| **可实现性** | **解锁条件**：定三件事——① 基线存哪（建议 `eval/perf-baseline.json`，进 git；或 `.tmp/`，不进 git）；② 存什么（每档的 `min/p25/中位/p75/max/n/warmup/机器标识`，缺一项就无法复算）；③ 什么时候更新基线（建议：只在**显式发版**时更新，否则基线会被日常抖动同化）。**判定方法**：连续跑两次同档，第二次能打印「与基线对比：区间重叠 / 明显更快 / 明显更慢」三档之一 |
| **当前状态** | **未解锁**——落盘格式与刷新策略都没定 |

## 为什么现在不能做

它引入一类**新的持久数据**（性能基线），而这仓库的规矩是「数字必须可复算、同一件事只有一处说了算」。
基线一旦进 git，就会和 `eval/split-manifest.json` 一样成为冻结对象——**先想清楚刷新规则再落盘**，
否则会出现「基线随每次运行漂移，于是永远没有回归」的假绿。

## 解锁后的验收

- 同档连跑两次，区间重叠时**不许**报「更快/更慢」，只报「重叠」；
- 人为注入一次退化（例如把 `--budget-ms-per-1k` 调小或改慢 `card_text`）能稳定报「明显更慢」；
- 基线文件有 `机器标识` 字段，跨机器比较时自动拒绝（不能拿 CI 的数字判本地）。
