# 待解锁台账（pending）

> **这里放「已经确定要做、但被一条可判定的前置卡住」的事。** 一条一个文件。
>
> 它补的是另外两份文档之间的空隙：
>
> | 层 | 在哪 | 回答什么 |
> |---|---|---|
> | 想法池 | [`../backlog.md`](../backlog.md) | **想做，但今天不该做**——连解锁条件都还没有 |
> | **待解锁台账（本目录）** | `pending/` | **决定了要做，但有明确的解锁条件**；条件一到就能开工 |
> | 已发生 | [`../CHANGELOG.md`](../CHANGELOG.md) · [`../withdrawn/`](../withdrawn/README.md) | 已发布的改动 / 已撤回的宣称 |
>
> 为什么需要它：边界最容易变成「口头共识」。写成文件后，**每次阶段性完成就扫一遍**，
> 跑各自的解锁判定——能解锁的搬出去做，不能的留着继续等，谁也不用凭记忆判断。

## 文件命名

`P` + 编号 + `-` + 英文短名 + `.md`，编号从 `P1` 递增、**不复用**；中文标题写在文件里。

## 每条必须写清四样（`tools/audit_docs.py` 会检查）

| 字段 | 为什么必须有 |
|---|---|
| `目标版本` | 判断它属于哪一批；避免「这件事到底排在哪」变成悬案 |
| `想法` | 要做的是什么（一句话 + 必要细节） |
| `可实现性` | **解锁条件 + 判定方法**（一条命令、一个读数）。没有这条就不是待解锁，是许愿 |
| `当前状态` | `未解锁` / `部分解锁` / `已解锁待做` / `已做`（做完就搬走，文件保留作为记录） |

## 阶段检查（什么时候来调用本目录）

**每个阶段收尾时**（发一个版本、或完成一个编号项），按这个流程走一遍：

1. 扫 `pending/*.md`；
2. 对每条的「可实现性」里的判定方法**真的跑一遍**（不是看一遍）；
3. 三档结论：
   - **已解锁** → 搬进待办、开始做；做完把文件里 `当前状态` 改成 `已做`（文件不删，留作记录）；
   - **部分解锁** → 改「当前状态」，并写清「还差哪一条」；
   - **仍未解锁** → 不改（也可以顺手把判定方法写得更可执行）。
4. 如果某条的解锁条件被证明**永远不会满足**（比如前提被撤回），就把它搬去 `backlog.md` 或
   当作「不做」处理，并在文件里写明原因。

## 纪律

1. **一条一件事。** 混在一起就没法单独判定解锁。
2. **解锁条件必须可判定**：能写出一条命令或一个数值阈值，才算数。
3. **不许在别处重复记**：`backlog.md`、`HANDOFF.md` 只写「见 pending/PN」，不复制内容。
4. **文件永不删除**：它记录的是「当时为什么还不能做」，删掉等于把判断依据抹掉。
