### 0.1 第 2、4 条为什么这么定（这两处最容易只改一半）

第 2 条和第 4 条都关于「衰减」，但改的是两件不同的事，必须分开看：**第 2 条改的是层级参数取哪个值，第 4 条改的是用这些参数怎么算。**

**(a) T1 为什么取 365 天，而不是「不衰减」**

| 选项 | 后果 | 判断 |
|---|---|---|
| 按 §7 注释：T0/T1 都不衰减 | T1 的 decay 恒为 1.0，即 0.25 分项永远拿满。一条三年前的长期偏好在排序上永远压过昨天刚确认的事实 | ✗ 会让排序失去时间敏感性 |
| 按 §4 表格：T1 = 365 天 | 一年后 decay 降到 0.5，但**入选与否不受影响**（T1 硬门无条件通过），只是与其他卡比较时排序下降 | ✓ 采用 |

关键在于区分**入选**与**排序**：T0/T1 的 `passes_gate` 是无条件通过，所以「衰减」永远不会让 T1 卡消失或取不到原文；它只决定 T1 卡在上下文里排多前。因此「365 天」既不违背「长期关键」的定位，又保留了时间敏感性。

另需说明 v1.0 自身的一处不一致：§4 说 T1「默认召回」，§7B 说「T0-T1 无条件加入」。v1.1 取**无条件加入**——「默认」是不可判定的措辞，无法写成代码。

**(b) 从 `exp(-Δ/τ)` 改成 `0.5 ** (Δ/half_life)` 的实际影响**

两者不是同一个函数：前者在 Δ = half_life 时衰减到 0.368，后者才是 0.5。也就是说 v1.0 的「半衰期」实际衰减得比标注值**更快**：

| Δ / half_life | v1.0：`exp(-Δ/hl)` | v1.1：`0.5 ** (Δ/hl)` | 折算后的实际半衰期 |
|---|---|---|---|
| 0.5 | 0.607 | 0.707 | — |
| 1（正好一个半衰期） | **0.368** | **0.5** | v1.0 实际只有 0.693×标注值 |
| 2 | 0.135 | 0.25 | — |

代入 weight=0.25：T4（30 天半衰期）在闲置 30 天时，decay 分项从 v1.0 的 `0.25×0.368=0.092` 变为 v1.1 的 `0.25×0.5=0.125`。**注意这里有两种说法，引用时必须指明是哪一种**：按衰减项本身算，它高了 **35.9%**（0.125 / 0.092 = 1.359）；按「从 1.0 掉下来的幅度」算，下降幅度只小了 **20.9%**（0.5 / 0.632 = 0.791）。这是「不改变任何层级参数、却显著改变召回行为」的一处，所以必须显式记录，否则调参会得到与文档不符的结果。

另外补上 v1.0 完全没提、但一动代码就会卡住的三件事：**`now` 注入**（§5.4）、**Token 预算装箱算法**（§6）、**数据库约束与迁移**（§3.4）。

## 1. 三层架构与唯一真相源

| 层 | 存什么 | 格式 | 真相源 |
|---|---|---|---|
| 原始层 | 所有对话/文档原文 | `raw/<day>.jsonl`（不可变、只追加）+ `chunks/`（按帧冷存） | `raw/` 是内容真相，`source` 表是寻址真相 |
| 记忆卡层 | 压缩后的短卡 | SQLite `card` / `claim` 表 | **SQLite，唯一** |
| 索引层 | 全文 + 向量 + 图 | FTS5（`card_fts`）+ sqlite-vec（`card_vec`）+ `entity*` 表 | 派生数据，可重建 |

```
moonshadow/
  memory.db                     # 唯一真相源：card / claim / source / cursor / entity
  raw/2026-10-01.jsonl          # 不可变追加日志，一行一条消息
  chunks/2026-10-01.zlib        # 冷存分帧容器（zstd 可用时同名机制换 codec）
  chunks/2026-10-01.zlib.idx.json
  profile.md                    # 人工维护的实体与偏好白名单
  eval/gold/*.json              # 金标准集（Phase 2.5）
  src/moonshadow/*.py
  tests/  examples/  ddl.sql  schema.json
```

**不变式**：删除 `memory.db` 必须能从 `raw/` 完全重建索引层；反过来不成立（原文是终极真相）。

## 2. T0-T9 分层定义（修正版）

| 层级 | 含义 | 半衰期 | 召回策略 | 原文保留 |
|---|---|---|---|---|
| T0 | 永久核心：身份、硬约束、安全、法律 | **0（不衰减）** | 无条件加入 | 永久 |
| T1 | 长期关键：长期偏好、核心目标、关系 | 365 天 | 无条件加入 | 永久 |
| T2 | 季度关键：项目决策、重要承诺 | 180 天 | 相关（score>θ）或存在未完成事项 | 永久 |
| T3 | 月度重要：近期待办、截止 | 90 天 | 同上 | 永久 |
| T4 | 周度重要：一般方案、讨论结论 | 30 天 | 卡龄 ≤30 天 且 score>θ | 永久 |
| T5 | 日常事实：一般信息、偏好片段 | 14 天 | 同上（v1.0 的「低权重召回」并入此条） | 永久 |
| T6 | 短期上下文：当前任务细节 | 7 天 | 卡龄 ≤7 天 且 score>θ_high | 90 天 |
| T7 | 临时细节：中间推理、草稿 | 3 天 | 同上 | 90 天 |
| T8 | 低价值：寒暄、确认 | 1 天 | 仅显式回溯请求 | 90 天 |
| T9 | 噪音：无意义内容 | 1 小时 | 仅显式回溯请求 | 7 天 |

**层级规则（可执行版）**

1. 重要性定 T 层；时间只负责**衰减与召回**，不参与定层。
2. 规则引擎只能在 **T2–T8** 区间内调整层级：
   - **升 1 级**：近 30 天访问 ≥5 次 **且** 跨 ≥3 个独立会话；最高升到 T2。
   - **降 1 级**：闲置 > 2×半衰期 且 近 30 天零访问；每个日检周期最多降 1 级（滞回）。
   - **永不自动降成 T9**（T9 只能由抽取阶段判定为噪音）。
3. **T0/T1 不参与规则升降**，只能由抽取阶段显式声明；存在未完成事项的卡不降级。
4. 冲突不覆盖（见 §7）。
5. **衰减只影响排序，不影响入选**：T0/T1 的硬门是无条件通过，因此 `half_life_days` 再小也不会让它们「因为旧」而消失，只影响它们在上下文里的先后。详见 §0.1(a) 与 §5.2。

> 为什么夹逼：让「被检索到」直接换层级，会让噪音把 T8 一路升到 T2，摧毁分层的意义。所以升级既要求次数，也要求跨会话广度。

## 3. 记忆卡契约

`schema.json` 是**强制**契约，写入前校验（`validate_card`），实现为零依赖校验器。

### 3.1 必填字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | `^mem_[0-9]{8}_[a-z2-7]{10}$`，内容寻址 |
| `schema_version` | integer | 固定 `1`，为将来迁移留位 |
| `session_id` | string | 命名空间，多用户/多会话隔离 |
| `tier` | enum | `T0`…`T9` |
| `importance` | integer 1–10 | 唯一进入打分的「重要度」字段 |
| `network` | enum | `world` / `experience` / `opinion` / `observation` |
| `observed_at` | ISO-8601 带偏移 | 衰减基准时间 |
| `status` | enum | `active` / `superseded` / `source_expired` / `archived` |
| `source_ids` | array ≥1，唯一 | 回链；空数组直接拒收 |
| `summary` | string 1–500 | 短卡正文 |
| `dedup_key` | sha256 hex | `sha256(tier\|source_ids\|summary)`，唯一索引，保证幂等 |

### 3.2 可选字段

`valid_from` / `valid_to` / `half_life_days`（默认取层级值）/ `last_access` / `access_count` / `supersedes` / `superseded_by` / `entities` / `keywords` / `facts` / `decisions` / `todos` / `constraints` / `raw_quote` / `confidence`（**未知写 `null`，禁止编造**）/ `claims`。

`additionalProperties: false`：未定义字段一律拒收，防止提示词漂移悄悄污染契约。

### 3.3 claims 子结构

```json
{ "kind": "todo", "subject_entity": "张三", "predicate": "给出报价",
  "object": "报价", "polarity": 1, "due_at": "2026-09-30" }
```

`kind ∈ {fact, decision, todo, constraint, preference}`。**`claims` 是冲突检测与「观点演变」的唯一数据来源**，不是附注。

### 3.4 数据库约束

`ddl.sql` 里所有枚举都落成 `CHECK`，`tier`/`importance`/`confidence` 越界在 SQLite 层就被拒；`uq_card_dedup` 保证重放安全；`card_source` 表让「这条原文被哪些卡引用」可反查。

## 4. source_id 寻址与冷存分帧

### 4.1 寻址表（实现「精确回取」的关键）

```sql
source(id, session_id, day, line_no, byte_off, byte_len, sha256, created_at, is_archived)
UNIQUE(day, line_no)
```

回取路径：

- `is_archived = 0` → `seek(byte_off)` 后读 `byte_len` 字节；
- `is_archived = 1` → 定位 `chunks/<day>.<codec>` 的第 `line_no // frame_lines` 帧，解压后取 `line_no % frame_lines` 行。

两条路径都校验 `sha256`，不一致抛 `RawIntegrityError`。**逐字节一致是可证明的，不是承诺。**

### 4.2 容器格式

```
chunks/<day>.<codec>            压缩帧顺序拼接
chunks/<day>.<codec>.idx.json   每帧：first_line, line_count, offset, comp_len, raw_len, sha256
```

- 默认 `frame_lines = 1000`，`codec = zlib`（标准库）。
- 本机无 zstd：调 `chunks.register_zstd()` 或 `register_codec()` 即可切换，机制不变。
- 帧级 sha256 使容器损坏可被定位到帧，而不是「整天数据不可信」。

### 4.3 原文双写

`raw/<day>.jsonl` 归档后**不删除**：冷存是寻址副本，不是唯一副本。任何时刻都能从 raw 重算整个冷存与索引。

## 5. 召回：硬门 → 打分 → 装箱

### 5.1 打分：相关性是主轴，时间是门与有界修正

> 本节及 §5.1.1–§5.1.3 的**形式化推导、定理与证明、消融实验与威胁有效性**另见
> [`v1.1-weights.md`](v1.1-weights.md)（技术报告，论文体例）。本节只保留契约与结论；
> 所有数字以工具输出为准（`tools/run_rank_eval.py`、`tools/run_holdout.py`）。

**初稿方案（现行实现）**把时间当成 0.25 的加性分项：

```
score = 0.45·sim_norm + 0.25·decay + 0.20·(importance/10) + 0.10·match
```

这隐含一个假设：**1 单位「相关」可以换 1 单位「新鲜」**。但两者不同源——相关性回答「这是不是答案」，
时间回答「它是否还成立」——强行定汇率必然在某一类查询上出错。实测确实出错（§5.1.1 第 03 号用例）：
一张完全相关但一年前的决策卡，会输给一张只是沾边的刚发生的新卡。

**因此把时间的职责拆成三处，三处都不与相关性抢权重：**

| 职责 | 位置 | 说明 |
|---|---|---|
| 门 | §5.2 硬门 | 按层级限制参与竞争的卡龄窗口（T4–T5 ≤ 30 天、T6–T7 ≤ 7 天） |
| 有界修正 | `score = relevance × [floor, 1.0]` | 时间最多把相关性打 `floor` 折，**无法反转差距较大的相关性** |
| 冲突裁决 | §7 `claim.valid_from` | 同一 `(subject, predicate)` 上新旧冲突时，更晚者胜出 |

推荐方案（相关性权重和为 1，故 `relevance ∈ [0,1]`）：

```
relevance = 0.60·sim_norm + 0.27·(importance/10) + 0.13·match
modifier  = floor + (1 - floor)·decay        # decay = 0.5 ** (Δ天 / half_life)
score     = relevance × modifier
```

**`floor` 取固定值 0.62（已采纳）。** 取法要说清楚，否则就成了假精度：

- 开发集（11 条）的可行窗口是 **[0.608, 0.634]**，留出集（10 条）是 **[0.466, 0.664]**；
- 留出集窗口**完整包含**开发集窗口且宽 7.6 倍，因此**起约束作用的是开发集**；
- 采纳值取两者**交集的点（0.6210）**，理由是最小最大余量（minimax）：0.62 距下界 +0.012、距上界 +0.014；
- **留出集的作用是否掉 0.70，而不是确认 0.62**——0.55/0.60/0.63/0.64 在留出集上同样全对。

因此这个数的诚实表述是「**落在 0.61–0.63 之间**」，而不是「等于 0.62」。窗口宽度 0.026 由**3 条开发用例**
钉住（`03` 抬下界、`05`/`06` 压上界），少数用例决定参数，精度不可当真。

| 取法 | 状态 | 说明 |
|---|---|---|
| **固定下限 0.62（推荐并已采纳）** | ✅ 采用 | 开发集与留出集同为满分；无需任何意图识别 |
| 连续敏感度插值 | 🔶 保留实现 | 实测与固定值并列，**无增量**；仅在意图判错时把损失从「整体翻转」降为「程度偏差」 |
| 按意图硬切换 | ❌ 废弃 | 换上正确下限后开发集只有 0.909（低于固定值的 1.000），却要多一个 recall 0.5 的组件 |

连续敏感度（`scoring.time_sensitivity`）与 `INTENT_TIME_FLOORS` 的实现**刻意保留**，只为让
§5.1.1–§5.1.3 的实验可复现；它们不是推荐路径。敏感度估计规则：出现状态类标记趋近 1、
历史类标记趋近 0、无线索取 0（保守）。

**阈值必须重标**（floor 变化会整体下移乘性族的分数）：采纳 0.62 后标定结果为
`θ ≈ 0.398`（可行区间 [0.3878, 0.4074]）、`θ_high ≈ 0.366`（[0.3326, 0.3997]），
而现行 `0.35 / 0.55` **都落在区间外**。注意新区间比初稿更窄——降低下限在放宽时间话语权的同时，
也收紧了阈值的选择余地，这是同一笔取舍的另一面。

#### 5.1.1 对照实验（`tools/run_rank_eval.py`）

争论「权重该给谁」吵不出结论，因此做成可复现实验：**11 个人工标注用例**
（历史决策 / 当前状态 ×4 / 任务跟进 ×4 / 长期偏好 / 控制组，含负例与对抗用例），
每例给出候选与人工期望顺序；七种方案都调用**同一份真实打分代码**
（`scoring.score_card` 的 `scheme` 参数与 `scoring.reciprocal_rank_fusion`），
而不是在实验里另抄一份公式。

| 方案 | 融合算术 | 上下文来源 | 成对一致率 | 失败 |
|---|---|---|---|---|
| 加性（现行 0.45/0.25/0.20/0.10） | 加性 | 无 | 0.970 | 1/11 |
| **乘性修正（固定 floor 0.62）** | 乘性 | 无 | **1.000** | 0/11 |

| 两种分数 50/50 平均 | 分数平均 | 措辞推断 | 0.970 | 1/11 |

按意图拆分：

| 当前状态 | 1.000 | 1.000 | 0.000 | 1.000 | 1.000 | 0.500 | 1.000 |
| 任务跟进 | 0.917 | 1.000 | 1.000 | 1.000 | 1.000 | 1.000 | 0.917 |

**θ 标定（同一套用例，`calibrate_thresholds`）：**

| 方案 | 分组 | 负例上界 | 正例下界 | 区间 | 建议 | 现用值 |
|---|---|---|---|---|---|---|
| 加性 | `θ` | 0.5302 | 0.4932 | **不可行** | — | 0.35 |
| 加性 | `θ_high` | 0.4726 | 0.5263 | 可行 | 0.4995 | 0.55（区间外） |
| 连续插值 | `θ` | 0.3901 | 0.4597 | 可行 | 0.4249 | 0.35（区间外） |
| 连续插值 | `θ_high` | 0.3417 | 0.4059 | 可行 | 0.3738 | 0.55（区间外） |

**四个发现，按重要性排序：**

1. **（修正上一版结论）样本量会决定结论。** 在 6 个用例时三种融合算术完全一致（都 0.833），
   我曾据此写下「融合算术不重要」；扩到 11 个用例后，RRF 掉到 0.727，而同族的连续插值与
   50/50 仍一致（0.909）。**教训比结论更重要：小样本上的「无差异」不等于「无差异」。**
   现在的结论是：同族（乘性 + 同一 floor 来源）之间确实无差异；跨族（名次融合 vs 分数方案）有差异。

2. **加性方案的阈值在这套金标准上不可行——这是结构性缺陷的定量证据。**
   θ 标定要求「负例上界 < 正例下界」，加性方案给出 0.5302 > 0.4932：
   **不存在任何 θ 能把正负例分开**。原因正是 §5.1 指出的错误汇率——一张新鲜但几乎无关的卡
   （cos 0.15）靠衰减项白拿 0.25 分，总分反超真正相关的卡。连续插值方案在同一套用例上区间可行
   （0.3901–0.4597）。**排序一致率看不出这个差异（加性排序还更高），必须同时做阈值标定才能看见。**

3. **上下文来源的地位已被推翻（保留原记录以便追溯）。** 当时的结论是「同一套算术，floor 来源
   从措辞推断换成 oracle 意图，一致率 0.909 → 1.000，所以上下文来源是唯一没被榨干的维度」。
   §5.1.2 的 floor 扫描随后证明：真正的问题不是上下文不足，而是**默认下限 0.70 偏高**。
   采纳 0.62 之后，连「上下文来源」这个变量都消失了——意图切换、连续插值、固定值三者同为 1.000。
   **教训：把「机制不够」和「参数不对」混为一谈，会得出完全错误的技术路线。**

4. **同一处漏判，后果可能完全不同。** 第 08 号用例漏判但排序仍正确，第 06 号漏判则直接排错。
   所以「意图识别准确率」与「排序一致率」**必须分开报**——只看排序会以为识别没问题。

**推荐：**

- **机制**用「相关性主轴 + 上下文决定时间话语权 + 有界乘性修正」（`SCHEME_BLENDED`）。
  理由不只是排序一致率，更是**发现 2**：加性方案的阈值在这套金标准上不可行，而它的不可行来自
  「新鲜但无关的卡白拿衰减分」这个结构性缺陷，属于补再多信息也修不好的那一类；
- **上下文**用**连续敏感度插值**而非硬切换——连续插值在意图判不清时给出中间值，
  把误判的损失从「整体翻转」降为「程度偏差」；
- **RRF 保留为可选**：跨族差异确实存在（发现 1），但 RRF 在本实验更差；
  它真正的价值场景是**相关性分数本身不可信时**——余弦来自 embedding、importance 来自 LLM，
  量纲都可疑；RRF 只依赖名次，对这种不可靠性更稳健，代价是丢掉幅度信息；
- **分数平均（hybrid）不建议引入**：与连续插值在本实验数据上完全一致，却多一个参数与一处待调值。

**切换前必须做的三件事**（本次已把工具备好，但数据仍不够）：

1. 用 `calibrate_thresholds` 重标 `θ`/`θ_high`——现用 0.35/0.55 在乘性量纲下**都落在可行区间外**，
   直接切换会静默改变硬门行为；
2. 把 `time_sensitivity` 的召回从 0.500 提上去（见 §13 第 8 条）——这是当前唯一没被榨干的维度；
3. 按真实查询分布扩充用例集与负例集，再复核发现 2 是否依然成立。

**效力边界（必须一并说明）：**

1. `n = 11` 且期望顺序由人工标注，**只能验证机理，不能证明生产质量**；
2. 「硬切换」「连续插值」「RRF」「50/50」都是在本实验过程中逐步加入的，
   **存在过拟合这批用例的风险**；标记词表（`STATUS_MARKERS` / `HISTORY_MARKERS`）同样是人工拍定的；
3. 聚合一致率受**用例配比**主导（状态类占 4/11），**总分不能作为选型依据**，
   必须看按意图拆分的表、失败性质，以及阈值标定的可行性；
4. 阈值标定的约束**很弱**：参与标定的分数型负例只有 3 条（`θ`）与 2 条（`θ_high`）。
   区间可行是个积极信号，但样本量不足以据此定值；
5. 状态类查询更彻底的修法是**收紧时间窗（门）**，而非继续加大时间权重；该改动未被本实验覆盖，
   因为实验只对「已过门的候选」排序；
6. `intent_aware` 的 1.000 建立在 **oracle 意图**之上，是不可直接生产的数字——
   它在这里的价值是充当「意图识别完美时能达到的上界」。

#### 5.1.2 floor 扫描与逐用例可行区间（对 §5.1.1 推荐的修正）

§5.1.1 的结论建立在「按意图把 floor 分到 0.35 / 0.70 两端」之上。这里换一个更基本的问题：
**到底有没有一个全局单值能让全部用例通过？** 如果有，那套按意图切换的机器可能是多余的。
做法是把 floor 当自变量扫描 501 个取值（`sweep_floor`），算术固定为乘性修正。

**结果：存在，但窗口极窄。**

```
最优 floor=0.608 → 一致率=1.000
全通过窗口=[0.608, 0.634]，宽度=0.026（共 1 段）
```

把窗口按用例分解后，压力的来源一目了然（`case_floor_bands`）——**决定窗口宽度的只有两条用例**：

| 用例 | 可行 floor 区间 | 宽度 | 当前标记词方案选择 | 是否在区间内 |
|---|---|---|---|---|
| 01 历史决策 | [0.524, 1.000] | 0.476 | 0.700 | ✓ |
| 02 当前状态 | [0.000, 0.702] | 0.702 | 0.350 | ✓ |
| **03 任务跟进** | **[0.608, 1.000]** | 0.392 | 0.700 | ✓ |
| 04 控制组 | [0.000, 1.000] | 1.000 | 0.700 | ✓ |
| **05 状态·陈旧强相关** | **[0.000, 0.634]** | 0.634 | 0.350 | ✓ |
| **06 状态·无线索** | **[0.000, 0.634]** | 0.634 | **0.700** | **★** |
| 07 历史·含状态词 | [0.404, 1.000] | 0.596 | 0.525 | ✓ |
| 08 状态·弱信号 | [0.000, 0.986] | 0.986 | 0.700 | ✓ |
| 09 / 10 / 11 | [0.000, 1.000] | 1.000 | 0.700 | ✓ |

**由此得到三条修正：**

1. **「要不要按意图切换」是个伪二选一。** 全局单值 0.62 就能全对；真正的问题是
   「如何让 floor 落进一条很窄的可行带」——两种机制都只是达成它的手段。
2. **窄带由 03 与 05/06 的相互矛盾造成**：03 要求「无关但新鲜的卡不得压过相关的旧卡」（下界 0.608），
   05/06 要求「新鲜度必须能压过中等相关的旧卡」（上界 0.634）。二者**不是意图差异**，
   而是**相关性差距大小的差异**——这正是有界修正器在管的量，所以机制方向是对的，
   出问题的是**默认值取 0.70 偏高**，而不是缺少意图识别。
3. **「二分类意图准确率」是错的中间指标。** 它报了 3 个错误（07 误判、06/08 漏判），
   但按可行区间衡量只有 **1 个**错误：07 选的 0.525 落在 [0.404, 1.000] 内，
   08 选的 0.700 落在 [0.000, 0.986] 内——两者都是**无害错误**。
   正确的中间指标是 **floor 落带率**（当前 10/11），而不是意图标签猜得准不准。

**修正后的推荐（已采纳）：**

- **默认 floor = 0.62**（固定在代码常量 `TIME_FLOOR`），意图信号与连续敏感度都**不作为承重结构**。
  依据是 §5.1.3 的留出验证：0.62 是唯一在开发集与留出集上同时满分的固定值。
- **但 0.62 是在同一批用例上扫出来的，属于调参结果**，必须先拿到留出用例再采用——
  这与「按意图 0.35/0.70 来自人工判断、未经调参」之间**不是公平比较**：
  一个是拟合过的值，一个是没拟合的值。这一点必须在下次实验里用留出集消除。
- **意图识别不再是关键路径**（这一点修正了 §5.1.1 的排序）：它只影响 1/11 条用例，
  而 floor 默认值影响的是全体用例在窄带内的位置。

#### 5.1.3 留出验证：0.62 站住了，意图识别没必要（`tools/run_holdout.py`）

§5.1.2 的 0.62 是在开发集上扫出来的，因此必须用**留出集**检验它是不是过拟合。
留出集 10 条（`eval/holdout/`）在跑之前就已写完，期望顺序由一条**事前定好的原则**推导
（相关性差距大 → 相关性优先；差距中等 → 较新者优先；相关性相同 → 较新者优先），
与 floor 取值无关。标签也换了：留出集用 `needs_fresh`（答案是否依赖最新状态）而不是
status/task/historical——后者对「报价给到了吗」这类提问本来就没有客观答案，是 §5.1.2 暴露的标签缺陷。

| 策略 | 开发集 | 留出集 | 差值 |
|---|---|---|---|
| 全局 **0.70（现行默认）** | 0.818 | 0.800 | −0.018 |
| 全局 **0.62（开发集扫描最优）** | **1.000** | **1.000** | +0.000 |
| 全局 0.55 | 0.970 | 1.000 | +0.030 |
| 全局 0.50 | 0.939 | 1.000 | +0.061 |
| 全局 0.35 | 0.818 | 0.900 | +0.082 |
| 意图切换 默认0.70/状态0.35 | 0.818 | 0.900 | +0.082 |
| 意图切换 默认0.62/状态0.35 | 0.909 | 1.000 | +0.091 |
| 连续插值 默认0.70 | 0.909 | 0.900 | −0.009 |
| **连续插值 默认0.62** | **1.000** | **1.000** | +0.000 |

**结论：**

1. **能确认的只有「0.70 太高」，不能确认「0.62 就对」。** 留出集窗口 [0.466, 0.664] 完整包含
   开发集窗口 [0.608, 0.634] 且宽 7.6 倍，所以它只否掉了极端值（0.70 > 0.664 失败）。
   0.55/0.60/0.63/0.64 在留出集上同样全对。**采纳 0.62 是因为它是交集的 minimax 点，
   不是因为它被独立验证过**——这一点此前被我写成「留出集验证了 0.62」，是错的。
2. **意图识别是负收益**——换上正确默认值后，意图切换在开发集只有 0.909（**低于**纯全局的 1.000），
   留出集并列 1.000。**没有增量，却引入一个 recall 仅 0.5 的组件。**
3. **所有意图漏判都变得无害**——三个漏判全部落在各自可行区间内，一个都没造成排序错误。
4. **窗口宽度只由少数用例决定**：开发集 3 条（`03`/`05`/`06`）、留出集 2 条（`H02`/`H04`），
   合计 5 条 / 21 条。所以「0.62」这个精度来自我手写的几个数字互相挤压出的缝隙，
   换个数据点就能挪动它。

**最后一条边界**：留出集同样由人工编写、且与开发集共享同一套「数值世界」，
所以它检验的是**参数在同类设计假设下的泛化**，不是真实查询分布上的泛化。
真实分布数据仍然是不可替代的。

### 5.2 硬门（先定性，再定量）

| 层级 | 条件 |
|---|---|
| T0–T1 | 无条件通过 |
| T2–T3 | `score > θ` **或** 存在未完成 `todo`/active `claim` |
| T4–T5 | `卡龄 ≤ 30 天` 且 `score > θ` |
| T6–T7 | `卡龄 ≤ 7 天` 且 `score > θ_high` |
| T8–T9 | 仅当显式回溯请求（用户要原话/引用/具体来源） |

硬门的意义：把「不该进来的」在打分前拦掉，避免高分噪音挤占预算。**顺序不可颠倒**——先排序再过滤，会让阈值失去可解释性。

注意 T0–T1 这一行的含义：无条件通过意味着 `half_life_days` 对它们是「排序参数」而非「生存参数」。T1 卡闲置一年后 decay 只剩 0.5，可能排在更相关的新卡之后，但它**一定在上下文里**，也一定能按 `source_id` 取回原文（见 §0.1(a)）。

### 5.3 与 v1.0 召回策略的合并

v1.0 §4 与 §7B 对 T3、T5 的描述不一致，v1.1 以上表为**唯一权威**：T3 采用「相关或未完成」（更宽），T5 并入 T4 的 30 天窗口（§4 的「低权重召回」由 `importance` 与 `decay` 自然体现，不再单列规则）。

### 5.4 时钟注入（可测性前提）

衰减、升降级、有效期全部依赖「现在」。因此：

- 核心模块**禁止**出现 `datetime.now()`，一律通过 `Clock` 协议注入；
- 内部统一存 aware UTC，展示保留偏移；
- 测试与回放用 `FixedClock` + `advance()`，衰减结果逐位可复现。

## 6. Token 预算装箱

v1.0 给了 `Token预算` 变量，却没说装不下时丢谁。v1.1 定成确定性算法：

1. **常驻区无条件进入**：`long_term` 分区（T0/T1）不受配额限制。若它单独超预算，标 `over_budget=True` 并照常输出——身份与硬约束绝不被静默裁掉。
2. 剩余预算按配额切分，**区内按 score 降序贪心**：
   | 分区 | 配额 |
   |---|---|
   | 近期原文 | 30% |
   | 相关记忆卡 | 40% |
   | 决策与待办 | 20% |
   | 冲突提示 | 10% |
3. 装不下先**降级渲染** `full → lite`（lite = 只留 summary），仍装不下才丢弃并记录原因（`no_space` / `quota_exhausted`）。
4. 分区余额**滚入**下一分区，不浪费预算。
5. 同分按 `id` 排序 —— 同一输入必得同一上下文，否则生产事故无法复盘。

## 7. 冲突、取代与观点演变

### 7.1 数据结构

```sql
claim(id, card_id, kind, subject_entity, predicate, object, polarity,
      due_at, done_at, valid_from, valid_to, superseded_by)
```

### 7.2 判定与处置

- **冲突** = 同一 `(subject_entity, predicate)` 下 `object` 或 `polarity` 不同，且 `valid_from/valid_to` 区间重叠。
- 处置：旧 claim 填 `superseded_by`；旧卡 `status='superseded'` + `superseded_by`；新卡 `supersedes=[旧卡]`。**两行都留**，历史不删除。
- 召回时在 `[冲突提示]` 分区同时给出新旧两条，并标注更晚者。
- **同源改写**（同一 `source_ids` + 同一 tier，摘要变了）由 `Store.put_card` 自动标记取代，避免重跑后出现两张 active 重复卡。

> 实现中的一处修正：卡 ID 若只由 `(日期, 会话, source_ids)` 派生，会把同一段原文合法抽出的「决策卡 / 待办卡 / 约束卡」撞成同一 ID 并静默丢弃。因此 ID 必须纳入 `tier` 与 `summary`，取代语义由取代关系承载。

### 7.3 观点演变

「用户对 X 的看法从 A 变成 B」= `SELECT subject_entity, predicate, object, valid_from FROM claim WHERE subject_entity=? ORDER BY valid_from`。**不需要模型即兴回顾**，Reflect 只负责把查询结果写成叙事。

## 8. 触发、幂等与游标

### 8.1 触发条件（沿用 v1.0，补约束）

会话空闲 10 秒 / 累计 4096 token / 累计 10 条消息 / 出现 T0–T2 信息 / 检测到冲突、决策或承诺。

补充规则：

- **单飞**：一个后台 worker；触发只置脏标记，绝不并发跑两个压缩任务。
- **游标**：`cursor(session_id, last_source_id, last_day, last_line)`，崩溃后从游标续跑。
- **幂等**：内容寻址 ID + `dedup_key` 唯一索引 + `INSERT OR IGNORE`；同一段原文重跑必须得到同一批卡与同一状态。
- **快路径**：T8/T9 用规则（长度、寒暄白名单、正则）判定，不进 LLM。

### 8.2 触发不进主循环

压缩永远异步；`Recall` 只读已落库的卡与原文，不等待压缩完成。

## 9. 精度保障

### 9.1 两级校验

**第一级（确定性，必须先跑）**：`verify.py` 用正则抽取原文里的日期、金额、URL、代码片段，检查它们是否至少被**引用该原文的某一张卡**保留。

- 作用域是「原文 → 整批卡」而非「原文 → 单卡」：一段原文合法支撑多张卡，按单卡校验会大量误报。
- 归一化后比对（去空格与千分位），避免「12 万」/「12万」误判。
- 否定词与条件句作为**软告警**（原文有、整批卡都没有则提示复核），不作为失败——它们的语义边界靠正则判不准。

**第二级（模型模糊校验）**：在硬关卡通过后追加，检查语义遗漏、条件方向写反等。**不得**取代第一级。

### 9.2 验收指标（v1.0 缺失）

指标必须是**一对**：只报保留率会被「什么都不压缩」钻空子，只报压缩率会丢字段。

| 指标 | 目标 | 当前（规则基线） |
|---|---|---|
| 关键字段保留率（date/amount/url/code） | ≥ 98% | 1.000 ✅ |
| 压缩率（原文 token / 卡 token） | > 1.0（越大越好） | **0.35x ❌ 未达标** |
| 原文回取 P95 延迟 | < 50 ms（单帧解压） | 单帧解压，未压测 |
| 回取字节一致率 | 100%（sha256 强制） | 100% ✅ |
| 冲突漏报 | 金标准集上为 0 | 冲突检测器未实现 |
| 重跑幂等 | 同输入两次运行产出完全一致 | 已有单测 ✅ |

基线压缩率 0.35x（即膨胀 token）的原因：SPEC §2 要求 T0/T1「保留原文」，基线把整段原文抄进
`raw_quote`，facts 又复述一遍。这是**符合规范的基线代价**，不是缺陷——它标出了「不丢字段」的
召回上限；模型抽取器必须在保持该保留率的前提下把压缩率做到 > 1，这也是 Phase 2 剩下的主要工作。
评测关卡（`tools/run_eval.py`）会在压缩率 < 1 时显式告警，避免 PASS 被误读为「压缩有效」。

## 10. 保留策略与遗忘

| 层级 | 原文保留 | 到期处置 |
|---|---|---|
| T0–T5 | 永久 | — |
| T6–T8 | 90 天 | 卡 `status='source_expired'`，摘要保留 |
| T9 | 7 天 | 卡降级归档，`source_ids` 保留但标记悬空 |

- 召回遇到 `source_expired` 的卡**必须显式提示**「原文已清理，摘要不足以精确引用」，不许假装还能回取。
- 全局开关 `retention.mode = never_delete` 供合规敏感场景使用。
- 删除必须留 tombstone：`source` 行不物理删除，只标状态，否则回链会指向「不存在」而非「已清理」。

> **未实现**：清理任务本身（Phase 5）。当前 `archive_day` 只归档不清理，因此默认行为是「永不删除」，比 v1.0 更保守。

## 12. 实现路线与验收

| 阶段 | 产出 | 验收标准 | 状态 |
|---|---|---|---|
| Phase 0 | `schema.json` + `ddl.sql` | 坏卡被强制拒收；枚举与范围落在 DB 约束上 | ✅ |

| Phase 3 | `recall.py`：FTS/向量/图/时间四路检索 + 打分 + 装箱 | 打分与装箱有确定性单测 | 🔶 打分 ✅ / 权重方案对照 ✅ / 装箱 ✅ / 四路检索 ⬜ |

**Phase 2.5 前移的理由**：全部价值押在「精度不丢」上。没有金标准集，Phase 3–5 写完也无法自证是否保住了日期和数字，只能靠感觉。

关卡当前是**通过但带告警**的状态：保留率达标、压缩率未达标。这正是它该有的样子——先量化，再优化。

## 13. 仍需拍板的开放项

1. **金标准集规模与来源**：多少轮对话、谁来标注、是否纳入真实使用日志。
2. **向量模型与维度**：`card_vec` 现为 `float[768]`，需与选定 embedding 对齐；无 sqlite-vec 时语义一路自动跳过（当前本机即如此）。
3. **阈值调参策略**：`θ=0.35 / θ_high=0.55` 是合理起点，但必须用 Phase 2.5 的数据回归。
4. **T9 是否真的允许丢弃**：当前默认永不删除，与 v1.0 的「可丢弃」相反，需确认存储成本可接受。
5. **敏感信息加密与密钥管理**：v1.0 提了「本地加密」但未定义 KDF、密钥存放与轮换；另需注意**向量本身也泄露信息**，「只同步加密摘要」不等于安全。
6. **多用户命名空间**：当前 `session_id` 具备隔离能力，但未定义跨用户召回是否可能发生。
7. **审计与备份**：`extraction_run` 已记录模型与提示词哈希，但未定保留期限与导出格式。
8. **时间话语权的默认值（已采纳，见 §5.1.3）**：默认 floor 已从 0.70 改为 **0.62**
   （`scoring.TIME_FLOOR`），留出集 1.000 vs 0.800。
   **遗留一项未做**：`θ`/`θ_high` 尚未按新量纲落地——标定建议为 `θ ≈ 0.398`、`θ_high ≈ 0.366`，
   而现行值仍是加性量纲下的 `0.35 / 0.55`。在新方案真正投入生产前必须替换，否则硬门行为静默变化。
9. **意图识别：结论是「不做」**（§5.1.3 结论 2）。二分类指标（recall 0.500）**高估了问题**——
   按 floor 落带率衡量只有 1/11 条错；而且换上正确默认值后，意图切换**没有增量**，
   却引入一个低召回组件。实现保留但仅供实验复现，不作为推荐路径。
10. **金标准用例配比与规模**：当前 11 个手写用例（状态类占 4/11），聚合一致率受配比主导，
   且**分数型负例只有 3 条与 2 条**——θ 区间的约束很弱。应按真实查询分布重做配比并扩大规模，
   否则 §5.1.1 的结论只能当机理验证。发现 1 已经证明：把用例从 6 条扩到 11 条，
   就足以推翻一个基于 6 条得出的结论。
11. **阈值重标定**：工具已就位（`calibrate_thresholds`），并已得出「现用 0.35/0.55 在乘性量纲下
    均落在可行区间外」的结论；但标定值本身受负例数量限制，须在扩集后重跑再定值。
12. **状态类查询的时间窗**：更彻底的修法是收紧这类查询的硬门窗口，而不是加大时间权重；
    该改动需要扩展实验框架（当前只对已过门的候选排序），尚未验证。
