# 想法池（backlog）

**这里放「重要但现在不该做」的架构想法。** 记下来是为了不被下一轮参数工作冲掉——
不是为了现在就动手。

规则：

- 每条想法写清 **状态 / 前置条件 / 来源**；前置条件尽量指向**可判定的东西**
  （某条命令通过、某个参数落地），不写「等有空」。
- 想法**不是承诺**，也不构成对现行契约的修改；采纳时才进 `v1.2-roadmap.md` 的版本规划。
- 现行协议与定值仍以 [`v1.2-spec.md`](v1.2-spec.md) 为准，本文件不改动任何结论。

## 自下而上的提升机制：T5–T7 草稿自动 consolidate 到 T2/T3

> **v1.2.x Roadmap 构想：针对自下而上的认知模式，探索 T5-T7 草稿自动 consolidate 到 T2/T3 的提升机制。
> 前置条件：当前 R1/R2 边界用例通过、f 分组参数落地。**

| 项 | 内容 |
|---|---|
| 状态 | **未采纳**（构想；本版范围外） |
| 目标版本 | v1.2.x Roadmap |
| 前置条件 | ① 路线图 §7.1 的 **R1 / R2 边界用例通过**；② **分组 `f` 参数落地**（路线图 §5 值表） |
| 来源 | 讨论中提出，经判断「极其重要，但不是今天该做的事」后归档 |
| 记入日期 | 与 v1.2 定值同批 |

### 为什么现在不做

前置条件不是形式：**提升机制会改变层级分布，而层级分布正是分组 `f` 与 `θ` 标定的输入。**
在 R1/R2 未通过、`f` 分组未落地之前引入它，等于把「参数还没定」与「系统行为还在变」
两件事叠在一起，届时无法归因是哪一边动了可行区。

### 与现有机制的关系（事实陈述，不含设计）

`src/moonshadow/scoring.py` 已有 `next_tier(...)` 与常量 `PROMOTE_MIN_ACCESS = 5`、
`PROMOTE_MIN_SESSIONS = 3`：**按访问量与会话数**的层级晋升，已在实现中。
本构想谈的是**自下而上**的 consolidate（草稿因自身成熟而上升）；
**触发条件尚未定义**——这正是动手前要先问清楚的地方（见下）。

### 待澄清（动手前必须先回答）

1. **触发条件**：什么算「草稿成熟到可以提升」？由模型判断、由人工确认、还是由规则（如被反复回取 / 与既有卡形成多条 `claim` 关系）？
2. **幂等与回滚**：提升后原文回链、`source_id` 与冷存是否保持不变（现行契约要求任何时刻可从 `raw` 重算）；能否降级回草稿。
3. **与 `access` 反馈闭环的关系**：被召回的更容易被召回，提升机制若也依赖召回历史，会与该闭环复合放大。
   现行约定是「自适应是产品目标，不是验证手段」——静态评测契约是否仍然适用。
4. **可测性**：现行评测是静态用例集（`eval/rank`、`eval/holdout`）。提升机制引入状态演化后，
   用例集需要「时间推进」语义，可能属于交互模拟器（路线图 §9 的 v1.2.x Roadmap 另一候选）的范畴。
5. **与精度关卡的关系**：提升会不会丢字段或改变 `render` 决策，需过 `tools/run_eval.py` 的保留率关卡。

## GPU 加速与多硬件适配：把「向量阶段」做成可插拔的加速层

> **构想（未实现）**：为**将来的**向量/相似度阶段提供可选加速后端（CUDA / 昇腾），
> 而默认安装仍是零依赖纯标准库。
> 前置条件：仓库内先出现真正的向量阶段——现在 `query_cos` 是调用方传入的
> 「卡 id → 相似度」映射，仓库里没有任何嵌入计算，所以**现在还没有可被加速的对象**。

| 项 | 内容 |
|---|---|
| 状态 | **未采纳**（构想；本条目讨论的是「将来那个阶段」的加速层，不是现有代码的优化） |
| 目标版本 | v1.2.x Roadmap（探索线之后的工程件） |
| 前置条件 | ① **向量阶段落地**：`query_cos` 由算出来的相似度提供而非调用方传入（判定：存在产出 `query_cos` 的模块及其用例）；② 纯 Python 参考实现全量跑通并留读数（判定：`run_rank_eval.py` 退出码 `0`，七方案一致率与今日相同）；③ 加速层与参考实现**逐值一致**（判定：同输入下相等，容差 `1e-6`） |
| 来源 | 讨论中提出（GPU / 多硬件 / 国产算力的产学研方向），核对本仓库现状后归档 |
| 记入日期 | v1.2.x Roadmap 封存之后 |

### 三层，各自的定位不同

1. **加速层（可选）**：用 CuPy / Triton 写独立算子后端，只负责「批量相似度」这一件事；
2. **适配器（必须）**：同一接口两套实现，**无显卡时自动回退到纯 Python**。回退不只是为了能跑，
   更是为了**可复现**：评审与 CI 上必须能在没有 GPU 的机器上复算同一批数字；
3. **田野调查（研究性）**：把算子迁到华为昇腾（Ascend）生态，记录「哪里踩坑、怎么优化」——
   它产出的不是代码而是**可引用的工程记录**，是产学研结合里最容易做出差异的那部分。

### 为什么现在不做（两条，都是硬约束）

- **还没有可加速的对象**：`scoring.select` 收的是 `query_cos: Mapping[str, float]`，相似度由外部给。
  在向量阶段存在之前，加速层没有输入——现在写 GPU 代码只能写出一个没有调用者的模块。
- **会打破本仓库最强的性质**：README 的第一条特点是「纯 Python 标准库、零第三方依赖」。
  引入 CuPy / Triton 必须做成 **opt-in extra**：默认安装的依赖集不变，加速层缺失时自动回退。
  这条不是洁癖——它决定了别人能不能在五分钟内复算我的结果。

### 与现有机制的关系（事实陈述，不含设计）

- 打分与装箱都是纯函数，与「相似度从哪来」解耦；这正是加速层可以只替换一个函数的前提。
- 评测判据（保留率、C6、C8、C1）与 `pack` 的确定性**不依赖**相似度算法：
  换后端不应改变任何判据读数——若改变，说明加速层有 bug，而不是「效果不同」。
- 现行 `tools/run_rank_eval.py` 的七方案对照可直接当加速层的**回归测试**：一致率必须仍是 `1.000`。

## `build_summary` 的回填：长消息上「先出现的字段类型」会吃光预算

> **构想（未实现）**：把关键字段回填从「按类型顺序收干」改成「按类型轮转」，
> 让日期不再独吞 `SUMMARY_MAX_CHARS`。
> 前置条件：**愿意为它把全仓库的压缩率读数重算一遍**（见下）。

| 项 | 内容 |
|---|---|
| 状态 | **未采纳**（缺陷已量化，代价也已量化，判断是现在不划算） |
| 目标版本 | 等 LLM 抽取器接管 `summary` 之后自然消失，或与下一次读数重算合并做 |
| 前置条件 | 有人愿意同步更新 `v1.2-spec.md` §9、`v1.2-weights.md`、汇报材料里的分层读数 |
| 来源 | 把一份真实聊天记录按 300 字切块导入记忆库时发现（`HANDOFF.md` §7 那组实验） |
| 记入日期 | 修 `SUMMARY_MAX_CHARS` 的同一天 |

### 事实（都是实测）

`extract_key_fields` 一次把某一类型的所有值吐完（先日期、再金额、再链接、再代码），
`build_summary` 照这个顺序回填。字段多到超过 `500` 字时，日期就把预算吃光：
一段带 79 个日期 + 79 个金额的文本，回填后只剩日期，`万` 一次都没进 summary。

改成按类型轮转能修掉它，代价是金标准集的卡 token 从 `10,049`/`17,364` 变成
`10,059`/`17,368`，平均压缩率 `0.498x → 0.497x`——**spec、weights、汇报 PPT 的读数都要跟着改**。

### 为什么现在不做

收益只在「关键字段超过 500 字」的长消息上，而现行基线抽取器的目标输入是
**一条消息**（短句）；这类长消息来自「把整段对话灌进记忆库」这种非常规用法。
为一个边缘输入让全仓库读数漂移一次，不划算——**等 LLM 抽取器接管 summary 时一起做**。
在那之前，`build_summary` 的 docstring 里写明了这条已知缺陷。

## `T4`/`T7` 的判据缺口：补分类器，还是把「10 层」改成「可达 8 层」

> **构想（未实现）**：`TIER_ORDER` 声明了 10 层，但 `classify_tier` 只有 `T0–T3` 关键词表 +
> `T5/T6` 兜底，**`T4`/`T7` 没有任何赋值路径**（连 LLM 抽取器也补不上，因为它不选层）。
> 前置条件：先决定要不要为「分层叙事」再付一次全量重标定的代价。

| 项 | 内容 |
|---|---|
| 状态 | **未采纳**（缺陷已量化，两条修法的代价都能算清；选哪条是产品决定，不是技术决定） |
| 目标版本 | 与 LLM 抽取器同一批；若选「收窄宣称」则可单独发布 |
| 前置条件 | ① 接受「改层级判据 → `f`/`θ` 全部重标定」；或 ② 若选收窄宣称，同步 `v1.2-spec.md`、`README.md`/`README.en.md`、汇报材料三处 |
| 来源 | 2026-11-05 对 `T0–T9` 做代码实况核查（`HANDOFF.md` §8.1）：`classify_tier` 无 `T4`/`T7` 分支；`extractor.py:203` 用同一函数分组 |
| 记入日期 | 同批（`docs/v1.2-summary.md` §6 缺陷 12–14） |

### 事实（代码级，可逐条复核）

- `compress.classify_tier` 的判定链是：`classify_fast_path`（T8/T9）→ `TIER_KEYWORDS`（只有 T0/T1/T2/T3 四组）
  → `OPINION_RE` 命中给 T5 → 含数字或时间词给 T5 → 否则给 T6。**没有 T4、没有 T7 的分支。**
- `extractor.py:203` 是 `tiers_of = [(message, classify_tier(message.text)) for message in messages]`，
  **tier 由规则判，模型只负责在同一层内合并成卡**。所以接上 LLM 抽取器之后，`T4`/`T7` 依然是 0。
- 实测两处一致：`run_eval.py` 的 25 条金标准分层读数里 `T4 = 0`、`T7 = 0`；87 条事实入库后同样为 0。
- 分类器的脆度（同一批实测）：把 10 层各自的官方中文描述原文喂进去，只有 T0/T1/T3/T6 能判回自己，
  `T2` 的描述（「项目季度关键：项目决策」）被判成 `T6`、`T5` 的描述被判成 `T1`——关键词是
  `决定/采用/确定/…`，抓不到「决策」这个词。

### 两条修法与必须先付的代价

| 修法 | 做法 | 代价 |
|---|---|---|
| 1 补判据 | 给 `T4`/`T7` 加关键词，或者让抽取器**自己输出** `tier`（而不是被规则分组） | 层级分布一变，`f`/`θ` 的标定输入就变：开发集窗、留出集窗、漂移实验**全部重算**；而留出集的一次性已经用掉（`v1.2-summary.md` §6 缺陷 3），等于下一个参数决策没有干净留出集 |
| 2 收窄宣称 | 文档/PPT 改成「宣称 10 层 / 可达 8 层 / 实测 6 层」 | 零代码代价；但「10 层」这个卖点要降级，且要同步 spec、两个 README、汇报材料三处——**改漏一处就会自相矛盾** |

### 为什么现在不做

`T4`/`T7` 的缺失**不影响任何已确认结论**：两集合排序 `1.000`、负例门审计 0 违规、漂移上界成立，
全部建立在「现有层级分布」上。真正受影响的是**对外叙事**（「十层记忆」），而叙事的问题该用
文档解决，不该用动公式解决。

**一条纪律**：在写成文案的几个数字之间，「10 层」是唯一一个**代码支撑不到的说法**。
要么补代码，要么改说法——**不许两样都不做**。

## 召回在 1000→1500 卡之间有一个 240 ms 的台阶

> **构想（未证实）**：这一段不是「变慢」，是**非线性跳变**——读库、相似度、装箱三者同时跳 `2.4–4.5` 倍。
> 最可能是 SQLite 默认页缓存（`cache_size` 默认约 `2 MB`）在这一区间装不下。
> **这是假设，没做 profiling。** 前置条件就是把它证实或证伪。

| 项 | 内容 |
|---|---|
| 状态 | **未证实**（`tools/stress_recall.py` 已能量到，归因没做） |
| 目标版本 | v1.2.x（可能与待办 #19「常驻区上限」合并做，两者都在动 `recall` 的热路径） |
| 前置条件 | ① **profiling 确认归因**：把 `PRAGMA cache_size` 提到 `-65536`（64 MB）重跑同一档，看台阶是否消失；② 若不消失，用 `cProfile` 定位是 `store.cards()` 的行解析还是 `card_text` 的 bigram 构造突增 |
| 来源 | `python tools/stress_recall.py --cards 1000,1500,3000 --repeats 5`：边际 `579` / `253` ms/千卡 |
| 记入日期 | 与压力测试门同批（v1.2.2 之后） |

### 事实（可复算）

| 卡数 | 中位 ms | 每千卡 ms | 相邻边际 ms/千卡 | max/min | IQR/中位 |
|---|---|---|---|---|---|
| 1000 | 91.8 | 92 | — | 1.07 | 1.2% |
| 1500 | 382.5 | 222 | **579** | **1.95** | 4.6% |
| 2000 | 517.7 | 259 | 369 | — | — |
| 3000 | 761.9 | 251 | 253 | 1.06 | 3.4% |

两条读数值得并排看：

- **边际从 `579` 掉到 `253`**：说明 1000–1500 之间有一次性成本，之后才回到平滑区。
- **`1500` 档 `max/min = 1.95` 但 `IQR/中位` 只有 `4.6%`**：这是**双峰**（最短 203 ms、中位 382 ms），
  而 IQR 这种稳健统计量对双峰**不敏感**。所以压力测试工具必须同时报 `IQR/中位`（判门）与
  `max/min`（诊断）——只报一个会漏诊。

### 为什么现在不做

它**不影响正确性**：所有 `run_*` 验证仍然全绿，一万卡也仍在绝对门限内。
它影响的是**规模上限**（`50000` 卡时一次召回 `18 s`），而规模上限现在还不在承诺里。
按「先量再改」的既有纪律，归因没做完就改 `pack`/`recall` 是赌博。

### 怎么验收（可判定）

- 若提高 `cache_size` 后台阶消失 → 归因成立，修法是**显式配置缓存**（一行 `PRAGMA`），
  验收：`stress_recall.py --cards 1000,1500` 的边际降到 `300` 以下；
- 若不消失 → 归因作废，改从 `cProfile` 结果找真凶，**本条降级为「已证伪」并改写原因**。

## >20000 卡的成本由二次项主导：要索引，不是放宽门槛

> **构想（未实现）**：召回成本在 `10000 → 20000` 之间边际从 `275` 升到 `339 ms/千卡`，
> 二次拟合给出 `c = +4×10⁻⁶`（凸，见 [`v1.2-perf-model.md`](v1.2-perf-model.md) §5）。
> 所以「把门限放宽」解决不了大规模——必须减少**每次召回**的工作量。

| 项 | 内容 |
|---|---|
| 状态 | **未实现**（成本已量化；`20000` 档实测已超 SLO 或贴边，判定不稳） |

### 事实（可复算）

| 区间 | 实测边际 ms/千卡 | 三模型 `T'(n)` |
|---|---|---|
| 5000 → 10000 | 275 | 仿射恒 `306`；幂律 `295`；二次 `301` |
| 10000 → 20000 | **339** | 仿射恒 `306`；幂律 `308`；二次 **`372`** |

**二次模型最接近实测的加速**，这就是「凸」的可测形式。

### 为什么现在不做

`10000` 卡（`2.7 s`）仍在 SLO 内，真实库现在只有 `87` 张卡。**为一个还差两个数量级才出现的
问题改 schema，是过度设计**——而且它依赖 `#19`（常驻区上限）先落地，否则预算本来就不够用。

### 怎么验收（可判定）

- `cProfile` 结论先落地成一句话（谁占了主要时间），**没有这句话不许改代码**；
- 改完之后：`stress_recall.py --cards 10000,20000` 的边际回到 `300` 以下，
  且 `1500 → 2000` 的 `369` 也一起降（说明台阶同源）。
