## 1 范围与排除项

### 1.1 本版只做一件事

把时间下限 `f` 从**单一常数**改为**按层级分组取值**：

```
m = f_{group(card)} + (1 − f_{group(card)}) · δ
```

### 1.2 明确排除：自适应半衰期

**不做** `h_new = h_base · (1 + α · log(1 + access_count))` 及其变体。理由：

| 理由 | 说明 |
|---|---|
| 未知量膨胀 | 自适应把未知量从「每层一个半衰期」变成「每层一对上下界 + 强化系数」 |
| 反馈闭环 | access 由「被选入上下文」增加，而是否被选入又取决于衰减速率——被召回的更容易被召回 |
| 双重复奖励 | 已有的层级晋升已经在奖励访问；再加半衰期延长会与之复合 |
| 不可静态验证 | 分数依赖访问历史，现有评测契约（静态用例）不再适用 |

自适应是**产品目标**，不是**验证手段**。它让验证更必要，不是更少。留待 v1.3 之后的独立版本。

## 2 机制

### 2.1 打分形式不变

相关性分与时间修正的结构与 v1.1 完全一致，唯一变化是下限由常量变为查表：

```
r = w_sim · σ + w_imp · (importance/10) + w_match · μ
δ = 0.5 ^ (卡龄 / 半衰期)
m = f_group + (1 − f_group) · δ
q = r · m
```

### 2.2 理论收益：从单一上确界到一族上确界

由可反转判定（v1.1 定理 3），设 A 为被比较的、B 为挑战者：

```
B 胜出 ⟺ r_A/r_B < m_B/m_A
m_i ∈ [f_{group(i)}, 1]   ⇒   m_B/m_A ≤ 1 / f_{group(A)}
```

**不反转的充分条件：`r_A/r_B ≥ 1 / f_{group(A)}`。**

即：**反转难度由「被顶掉的那张卡」所属组决定**，而不是由一个全局常数决定。
语义上这意味着「高层级卡难被新信息顶掉，低层级卡易被顶掉」——
这正是层级体系本来想表达的东西。

### 2.3 与 v1.1 的兼容性

单一 `f` 解是分组解的**特例**（所有组取同值）。因此：

- v1.1 的结论不会被推翻，只会被推广；
- 分组解的可行域必然**包含**单一解（若单一解可行）；
- 若单一解**不可行**而分组解可行，则分组不是优化而是**必需**——这正是可行性探测的发现。

### 2.4 不变量（必须在实现后依然成立）

| 不变量 | 内容 |
|---|---|
| 值域 | 相关性分与修正系数仍落在各自区间内；`f_group` 必须夹在 `[0, 1]` |
| 单调性 | 分数对相似度、重要度、匹配度严格递增；对卡龄严格递减 |
| 不衰减层 | 半衰期为「不衰减」哨兵的层级，其修正系数恒等于上限，与 `f_group` 无关 |
| 时间只向下 | 修正系数上界为 1，时间永远不能给分数加分 |

## 3 分组定义

### 3.1 分组方案：按层级三组

| 组名 | 包含层级 | 语义 |
|---|---|---|
| `high` | T0–T2 | 身份、硬约束、长期关键、项目决策 |
| `mid` | T3–T5 | 近期待办、一般方案、日常事实 |
| `low` | T6–T9 | 短期上下文、临时草稿、低价值、噪音 |

组名与层级归属是**结构性定义**，不是待定的数值。

### 3.2 为什么是「按层级分组」而不是「按 network 分组」

| 维度 | 按层级 | 按 network |
|---|---|---|
| 标签来源 | 每条用例已带 `tier` | 用例不带 `network`，需补标注 |
| 赋值可靠性 | 由抽取器的层级判定给出，是系统主分类 | 见下 |
| 现有基础设施 | 排序扫描、可行区间工具均已按 tier 工作 | 需新建 |

关于 network：诊断实验（`tools/run_network_eval.py`）显示，**赋值本身不是瓶颈**——
一个四类词汇的规则即可接近 schema 上限，问题在于分类法缺一个类别（§7.3）。
但 network 分组仍需给排序用例补标注，因此**不在本版范围内**。

### 3.3 为什么不是「逐层一个 f」

逐层意味着**用少量用例去定多个参数**。当前正例覆盖在层级间严重不均（§7.2），
逐层会把过参数化推到不可验证的程度。分组是「在不增加不可验证参数的前提下拿到一族上界」的最小代价。

### 3.4 可选的更细分组（延后）

若将来覆盖率补齐，可考虑四组（把 low 拆成「短期」与「噪音」）或按 `network` 分组。
**两者都需要先补数据，不做前置实现。**

## 4 求解程序

严格按序执行，前一步未完成不进入下一步。

| 步 | 动作 | 产出 | 前置 |
|---|---|---|---|
| 0 | **修用例场景**：使每条用例的候选满足其层级的卡龄窗口；**不是把卡龄截到边界**，而是重写场景 | 修正后的用例集 | — |
| 1 | **补覆盖**：为当前零正例覆盖的层级各补若干候选，并压低占比过高的层级 | 覆盖均衡的用例集 | 0 |
| 2 | **加断言**：「任何用例的候选都不得违反其层级的窗口」——该断言在步 0 之前必定失败 | 一条由红转绿的断言 | 0 |
| 3 | **重扫单一 `f`**：确认单一解是否仍然可行 | 单一解可行区间或「不可行」 | 0–2 |
| 4 | **重扫分组 `f`**：三组网格扫描，分别对开发集与留出集求可行区，再取交集 | 交集与逐组区间 | 3 |
| 5 | **定值**：在交集内取最小最大余量点（两侧余量最均衡） | 三组 `f` 的建议值 | 4 |
| 6 | **重标定硬门阈值**：下限变化会整体移动乘性族分数，必须重标 | 阈值可行区间与建议值 | 5 |
| 7 | **落码**：常数改查表、分数函数接收组、守卫测试改语义 | 实现 | 5–6 |
| 8 | **切换默认方案**（若确定切换）：改默认打分方案并同步阈值 | 生产默认路径 | 7 |

**步 0 与步 1 是全部后续工作的前提。** 在用例前提错位的情况下调参，得到的数字不可信。

## 7 已知障碍与风险

### 7.1 数值尚未确定（本文件不写数字的根本原因）

可行性探测发现：把超窗候选**最小改动**修到窗口边界后，单一解的可行窗**急剧收窄**，
且与留出集**无交集**；分组解虽仍存在，但仅在「截到窗口边界」这一种修法下成立，
一旦把「陈旧」的卡改得更陈旧，分组解也消失。

**结论**：参数的可行区**由用例场景的写法决定**，不由数据决定。
所以必须先重写场景（步 0），才谈得上定值。

#### 数据扩充计划

| 项 | 内容 |
|---|---|
| **优先补齐** | `T9` 的**正例**（`T0`/`T7`/`T8` 的正例已由前两批补上；`T9` 至今只有负例侧） |
| **同时补齐** | **边界用例**：窗口边界（恰好等于窗口上界）、组边界（相邻层级同卡龄）、相关性相近但新旧不同 |
| **目标规模** | **正例数 80–100**（当前开发集 **49** 张；含留出集共 68 张）——**但规模不是唯一目标，也不是首要目标**；它只是「让约束来源多样化」的手段。每批的合入与否由下方「批次验收规则」判定，不由规模判定 |
| **节奏** | 分批补，每批补完即重扫并记录数值变动；**不一次写完再测**（一次写完会让「哪批用例移动了窗口」无法归因） |
| **每批的纪律** | ① 先写用例、后跑扫描；② 期望顺序由既有原则推导，不由试跑结果反推；③ 新用例必须满足自身层级的卡龄窗口与硬门前置；④ 补完立即跑 `run_case_audit.py`，违规数必须为零 |

**为什么规模不是目标**：正例数是约束量的上界——每个参数至少需要若干条用例
才能真正约束住它。当前正例由少数用例钉住可行窗（§7.4），扩量的目的是让「钉住边界的用例」
从少数变成十几条，而不是追求统计意义上的样本量。

但**规模只提供上界，不提供约束**：第一批实测已证明，10 条新增用例里 8 条对可行区毫无影响。
因此**不得以「正例数达到 80–100」为唯一目标**；规模达标而约束产率为零的批次，与没补一样。

#### 批次验收规则（硬性；不满足即拒绝合入）

| 编号 | 规则 | 判定量 |
|---|---|---|
| **R1** | 每一批新增用例，**必须包含至少 3 条候选分差 ≤ 0.05 的边界用例** | 边界用例 = 该用例期望次序中**相邻候选对**在当前采纳参数下的**最小分差 ≤ 0.05**，**且该用例在当前采纳参数下排序正确**（只满足前者是失败用例，不是边界用例） |
| **R2** | **若某批用例的约束产率为 0，则拒绝合入** | 约束产率 = 该批中「收窄可行区」的用例数 ÷ 该批新增用例数（须 **> 0**） |
| **R3** | **不得以「正例数达到 80–100」为唯一目标** | 规模只是上界；R1、R2 的判定先于规模判定 |

三条一律由 `tools/run_batch_audit.py` 计算，**不由人工目测**。

**为什么 R1 是硬的**：只有分数接近的候选对才会被参数改动翻转次序；分数差很大的用例
在任何参数取值下都通过，加多少条都不会移动可行区。
**为什么 R2 是硬的**：产率为 0 的批次只增加「用例条数」这一个数字，却让「用例很多」
掩盖「约束很少」——这正是第一批暴露的问题（产率仅 2/10，10 条里只有 2 条起作用）。

新增 10 条（`12`–`21`），覆盖 `T0`、`T7`、`T8` 正例与三类边界场景。

`run_grouped_floor.py`、`run_rank_eval.py`）。**重划切分把这些用例拆到了两侧**：
其中 `17`/`18`/`21` 在留出集，其余 7 条在开发集。

|---|---|
| 窗口与门前置违规 | **0**（`run_case_audit.py`） |

**判定的关键变化：第一批现在被拒绝合入。** 两处原因都值得记住——

1. `20` 的相邻分差在当前采纳下限下升到 `0.0533`，刚好越过 `0.05` 门槛，边界用例从 3 条降到 2 条；
2. 真正产生约束的两条（`17`、`21`）被随机划入留出集，开发集侧 7 条**全部无约束**。

**R1 / R2 是前瞻性规则**：重划切分会让一个旧批次在新开发集上不再达标。要让下一批可合入，
必须按 R1 补「分差 ≤ 0.05 **且**对 `f` 有约束」的**开发集**用例——这正是 R1 存在的理由。

| 判定 | `run_batch_audit.py`（**默认判定冻结后新增的那一批**） | — | **可以合入，退出码 `0`** |

这三条是**首批按 R1 设计**的用例：`23-t6-tight-race` 与 `25-t8-explicit-recall` 从**上侧**约束 `f`
（可行区间 `[0.000, 0.660]` / `[0.000, 0.662]`），`24-t7-borderline` 从**下侧**约束（`[0.500, 1.000]`）——
**两侧同时被夹住**，这正是第一批缺的东西（第一批 10 条里 8 条宽度为 `1.000`，无约束）。

**这条读数的意义**：R1/R2 不是空门槛——它**能被满足**，且满足后确实改变了结论
（单一 `f` 窗由 `0.215` 收到 `0.1600`，且用例集重新获得区分「要不要把时间话语权交给上下文」的能力）。
旧批 `12`–`21` 在开发集侧仍不达标，两条记录要一起看。

**最重要的一条：覆盖广度 ≠ 约束强度。**

按「新用例的可行区间宽度」衡量约束产率：

| 宽度 | 条数 | 含义 |
|---|---|---|
| `1.000`（完全无约束） | **8 / 10** | 任何下限取值都通过——它们只提供覆盖，不提供约束 |
| `0.875` | 1（`17`） | 微弱约束 |
| `0.985` | 1（`21`） | 微弱约束 |

也就是说，**第一批 10 条里只有 2 条（`17-explicit-recall-admits-t8`、`21-similar-relevance-newer-wins`）
真正收窄了可行区**——前者把 `T8` 放成了正例，后者让两张**同层级**候选只差新旧；
其余 8 条的两张卡分数相差太远，无论下限怎么取次序都不变。

**R1 只是预测指标，不是充分条件**：`14` 的相邻分差 `0.0091` 在门槛内，
但它的可行区间宽度仍是 `1.000`——「分差小」并不自动等于「有约束」，最终仍要看 R2 的实测产率。

**对扩充计划的修正**：后续批次不能只按「覆盖哪个层级」设计，必须同时按
**「两张候选的分数是否接近」**设计——只有接近决策边界的用例才会产生约束。
每批补完应计算**约束产率**（收窄可行区的新用例占比），作为该批的验收指标之一。

**一处已修掉的度量缺陷**：R1 原先只比相邻分差的**绝对值**，不含方向，于是「在当前采纳下限下
排序已经错了」的用例也会因分差小被算作边界用例。现在边界用例必须以
**在当前采纳下限下排序正确**为前提，排序错误的单列为失败项。
收紧前后读到的 R1 数字不可直接比较。

批次节奏也因此有了依据：**先小批、算产率、再决定下一批的场景类型**，
而不是一次写完 80–100 条（一次写完会让「哪批用例移动了窗口」无法归因）。

### 7.2 覆盖盲区

当前正例覆盖在层级间仍不均（两集合合计 68 张：`T5` 占 36 张，`T7` 仅 2 张、`T8` 仅 2 张），
且 **`T9` 仍是零正例覆盖**：第一批补了 `T0`/`T7`/`T8` 的正例，
第二批的 `22-t9-noise-blocked-by-tier` 只覆盖 `T9` 的**负例侧**（它按设计不承担参数约束），
`23`/`24`/`25` 补的是 `T6`/`T7`/`T8` 的**边界**场景。
这些层级对应的分组取值**没有数据支撑**——宽区间是「缺数据」，不是「有自由度」。
必须继续补齐，否则 `low` 组的取值仍部分依赖猜测。

另外两处覆盖缺口（切分重划带来的）：
**开发集侧 `T9` 零正例**（`T8` 已由 `25` 补上 1 张），
**分数型负例全部来自开发集**（留出集唯一负例的 `reason` 是 `tier`）——
因此 `θ` 的负例上界没有第二份独立数据。

### 7.3 分类法缺口（影响未来若走 network 分组）

诊断实验显示 `network` 的**赋值**不是瓶颈，但四类网络**装不下「待办/承诺」**：
这类内容在系统里已有归属（待办层级 + 待办类型的断言），但四类网络里没有对应项。

**处置选项**：① 增设第五类；② 明确把「待办/承诺」排除在 network 门控之外；
③ 放弃 network 门控，只按层级分组（本版即此选择）。

### 7.4 可行区的形状随用例集变化，且「最窄约束」会换组

分组扫描的可达集合**是否为各轴区间的笛卡尔积，取决于当前用例集**，必须每次实测而不是假定：

| 用例集 | 交集点数 | 形状 |
|---|---|---|
| 第一批加入前（11 + 10） | （旧记录，已不可复现：两集合此后都被改写） | — |
| 修正用例后、重划切分前（21 + 10） | 310（细扫 `0.005`） | 非盒形（外接盒 1800 点，17.2%） |
| 重划切分后、第二批前（23 + 9） | 12（粗网格 `0.055`） | 非盒形（外接盒 48 点，25.0%） |
| **第二批加入后（26 + 9，当前）** | **24（粗网格 `0.0395`）** | **非盒形**（外接盒 64 点，37.5%） |

**「最窄约束」在两个不同读数上不是同一件事，必须分开报**：

| 读数 | 逐轴范围 | 宽度 | 最窄 |
|---|---|---|---|
| 开发集粗扫（`run_grouped_floor.py` dev 段） | `high∈[0.4740, 0.6715]`、`mid∈[0.0000, 0.6320]`、`low∈[0.5135, 0.6320]` | `0.1975 / 0.6320 / 0.1185` | **`low` 严格最窄** |
| 两集合交集 | `high∈[0.5530, 0.6715]`、`mid∈[0.5135, 0.6320]`、`low∈[0.5135, 0.6320]` | **三轴均 `0.1185`（并列）** | **并列**；工具 `min()` 按字母序显示 `high`，**不代表 `high` 更紧** |

旧记录「最窄约束是 `mid`（T3–T5）」**已失效**：开发集侧改由 `low`（T6–T9）压住。
分组扫描的逐轴读数与采纳值的关系见 §5。

**读数须知**：交集是在**同一张全局粗网格**上算的保守内近似，逐轴精度只有 `0.0395`；
细扫（`0.0075`）只提高盒内分辨率，不改变交集范围。
因此「逐轴区间能否自由组合」「哪一轴最紧」这两句话**都必须连同用例集版本与扫描步长一起报**。

### 7.5 扫描步长必须整除被讨论的取值

若步长不能整除采纳值，网格会**漏掉真实可行点**，从而得出「某解不可行」的假结论。

本版**已把该断言从警告升级为阻断**：`rank_eval.require_step_divides` 在构造扫描时直接抛错，
`tools/run_grouped_floor.py` 与全局 floor 扫描都会命中；分组扫描默认改用
「全局粗扫 `0.0395` + 盒内细扫 `0.0075`」两阶段（两者都整除当前采纳下限）。

实测证据：`0.02` 这类步长会让工具**直接崩**，报错形状是
`ValueError: 分组 floor 扫描：步长 0.02 不能整除 0.5925`
（当时采纳值为 `0.605` 时的报错原文是「不能整除 `0.605`」，形状相同、数值随时间变化——
**引用报错原文时必须连同当时的采纳值一起写**）。
若确实要用不整除的步长，改用不依赖网格的单点求值，不要依赖网格。

### 7.6 参数耦合

下限、相关性权重、半衰期三者互相影响：任何一者改变都会移动其余的可行区。
因此**不得单独改动其中一项**；任一改动都要走完整的重扫程序。

### 7.7 「最稳点」会被扫描边界污染

在网格边界上取得的点，其到不可行集合的距离会被边界高估。
报告最稳点时必须标注它是否落在扫描域边界上。
